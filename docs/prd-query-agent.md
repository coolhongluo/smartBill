## 1. 一句话定位

**「对账单提问，得到有数字、有依据、诚实的回答。」**

用户用自然语言问自己（或家庭）的账单：「今年买水果花了多少」「相比去年哪类支出涨得最多」「我最大的一笔开销是什么」，Agent 理解问题 → 调用查询工具（代码计算）→ 组织成带依据的回答。

## 2. 背景：为什么现在要问数

现状分析页是**定时报告**，不是**问答**：

| 现状约束 | 出处 |
|---|---|
| 分析窗口固定 6 个月（`ANALYSIS_MONTHS = 6`） | `analysis-svc/index.js:75` |
| 11 个工具**月份锁定**——「日期由代码锁定」，模型不能问任意时间窗 | `tech/11-agent-harness.md` §5.2 |
| 读算分离：结论每天 0 点预生成，页面只读结果 | `02-analysis-rules.md` §1 |
| 用户无法即席提问：跨月、跨类目、任意对比、Top N、明细检索都不支持 | — |

问数 Agent 补的是**即席查询**：任意时间窗 × 任意类目 × 对比/聚合/明细。

## 3. 与现有分析页（insight agent）的关系：互补，不是替代

| 维度 | 分析页 insight agent（现状） | 问数 Agent（本 PRD） |
|---|---|---|
| 触发 | 定时 0 点 / 手动「立即分析」 | 用户每次提问即时触发 |
| 窗口 | 固定 6 个月 | 用户指定（受上限约束，见 §7.4） |
| 延迟 | 不在用户路径（读算分离） | **在用户路径**，必须控预算（见 §7.6） |
| 输出 | 落库洞察 + 省钱建议 | 一次性回答，**不落 insight 库** |
| 数字 | 代码算（bill-stats.js） | **同样代码算**（铁律不变，见 §5.1） |
| 落库 | `users/${openid}_insight` | 问数结果不落 insight 库；**会话历史**落 `users` 集合（`${openid}_askhistory_${sessionId}`，V1 只做存储底座，历史查询 UI 留 V1.1） |

> 问数结果不进 `saveInsight` 白名单、不碰 insight 文档结构，因此**不连动** `db/index.js:266-288` 的字段白名单坑。若 V2 要「把问数结果保存成分析」，那时再谈落库结构。

**V1 明确不加的维度（决策 8）**：账户筛选（微信/支付宝/现金/卡）、数据质量元查询（记账天数/补记率/无备注笔数）、星期/周末锚点（「上周末」「工作日 vs 周末」）、时段分析（几点花钱，V2）。均不进工具入参。

### Q1 聚合查询 ——「今年买水果花了多少」

- **口径**：按末级/二级/一级类目聚合 `sum(amountCent)` + 笔数 + 占比，时间窗由用户指定。
- **类目解析**：模型把「水果」映射到类目树（复用 `category-preset.js` 带 ID 的类目树注入，防幻觉 —— 曾实测只给名称列表幻觉率 14%，`tech/11-agent-harness.md` §3.3）；**模糊/命不中时反问确认，不猜**。
- **占比与总额由代码算**；模型只转述。
- **无数据时**：明确说「X 时间窗内没有『水果』类目的记录」，禁止编造。

### Q2 对比查询 ——「相比去年，哪类支出涨得最多」（✅ 已确认纳入 V1）

- **口径**：两个时间窗聚合 → 代码算变化额、变化率、方向（±1% 一律 `flat`，复用 `bill-stats.js` 口径 `tech/11-agent-harness.md` §5.5）→ 按类目分解出 Top 驱动。
- **同比诚实降级（不可妥协，沿用 PRD v3 口径）**：去年同窗无账单或有效笔数 < 3 → 返回 `hasYoYBaseline: false`，文案「记账未满一年，明年此时可看同比」，**禁止用其他基线冒充同比**（`22-roadmap.md` §2 F2）。
- **依赖**：同比需 13 个月数据窗口，**与 PRD v3 M1 合并实施（已确认，见 §9 依赖）**。
- **局部同期对齐**：「本月前 10 天 vs 上月前 10 天」—— 两窗口长度不等时，代码按**较短窗口的起止日**对齐另一窗口（如本月 1-10 日 vs 上月 1-10 日），变化率以对齐后的等长窗口计算；答案必须标注对齐口径。

### Q3 Top N / 极值 ——「我最大的一笔开销是什么」

- 代码排序后返回 Top N 明细（含金额、日期、类目、备注）。
- **双维度排名**：「哪类笔数最多」按 `count` 排，与金额排名是两回事 —— 工具出参区分 `byAmount` / `byCount`，模型不得把笔数排名说成金额排名。

### Q4 趋势 ——「每个月吃饭花多少」

- 代码按月聚合出序列，缺失月补 0；模型只描述形状（「逐月上升」等定性词）。

### Q5 明细检索 ——「上个月备注里有『礼物』的账有哪些」

- 代码侧按**备注关键词**过滤，返回逐笔 + **代码预聚合**的 sum/count（模型不得自己加总）。
- ⚠️ 搜索走**应用侧过滤**，不走数据库正则 —— `db.RegExp` 会毁掉 `test-persist.js`（`12-data-model.md` §6.4）。
- ⚠️ 账户/来源筛选 V1 **不做**（决策 8）：工具入参不含 `account`/`source`，模型若收到此类问题回答「暂不支持按支付方式/记账方式筛选」。

### Q6 周期消费 ——「我话费平均每月多少」

- 跨月窗口的周期检测。⚠️ **不能复用 `calcRecurringPatterns`**：它入参是单月数组，检不出月付订阅（`23-change-impact.md` §3.3 实测）—— 问数版必须是跨月窗口的纯函数。

### Q7 节假日锚点 ——「双十一花了多少」「去年春节花了多少」（✅ 决策 5：完整农历）

- **公历节日**（双十一、618、双十二）：锚点表硬编码。
- **农历节日**（春节、中秋、端午等）：引入农历换算库（见 §9 依赖），代码把「春节 2025」解析成具体公历日期区间；模型只选锚点枚举（`spring_festival` + 年份），**不自己算农历日期**。
- **节日窗口口径（✅ 已确认全部，决策 11、12）**：

| 节日 | 窗口 | 说明 |
|---|---|---|
| 双11 | **11.1 - 11.11** | 预售期口径（不只看 11.11 当天） |
| 618 | **6.1 - 6.18** | 与双11 同逻辑 |
| 双12 | **12.1 - 12.12** | 与双11 同逻辑 |
| 春节 | **除夕 - 正月十五** | 覆盖年夜饭、走亲访友、元宵 |

- 答案必须标注采用的窗口（证据卡附「按 11.1-11.11 预售期计」）。
- 无数据 → 诚实降级（同 Q1）。

### Q8 归因解释 ——「为什么这个月花多了」（✅ 决策 6：事实+归因）

- **驱动分解**：总变化额按类目拆解（涨多少、降多少），代码算出 Top 驱动类目（与 PRD v3 F2「驱动因素分解」**合并实现**，禁止两套）。
- 模型只表述「Top 3 驱动是 X/Y/Z，合计贡献 N%」，**金额与贡献率全部代码算**。
- 表述基调：**陈述事实，不评判用户**（PRD v3 坑 #9，`22-roadmap.md` §7）—— 说「餐饮多花了 180」，不说「你花得太多了」。

### Q9 家庭查询 ——「全家在哪类花最多」（✅ 决策 7：只聚合不比较）

- 聚合口径同个人（§5.5），数据源 family_bills。
- **禁止回答成员间比较**：「谁记的账最多」「谁在餐饮花最多」一律回答「我只统计全家整体，不做成员间比较」。prompt 铁律 + 测试用例双重保障。

### 明确不答的问题（V1）

| 问题类型 | 处理 |
|---|---|
| 「怎么省」「该不该买」（建议类） | 「我不给省钱建议，分析页有详细建议」+ 引导（§5.4） |
| 成员间比较 | 「我只统计全家整体」（Q9） |
| 收入/结余/预算/预测/投资（§10 非目标） | 「这不是我的能力范围」+ 一句解释 |
| 账户/来源/星期/时段筛选（决策 8） | 「暂不支持，V1 支持：时间、类目、备注关键词」 |

以上所有拒绝场景：**明确说不支持 + 一句原因，绝不编造数字蒙混**。

## 5. 核心口径（与既有铁律的关系）

### 5.1 数值铁律不变 —— 问数是铁律的延伸，不是例外

```
提问 → ask agent（理解意图 + 选工具，看不到原始账单）
     → 查询工具（代码捞账单 + 纯函数聚合，唯一算数字处）
     → 结构化统计 + 证据 → 模型组织语言 → 数字引用校验
```

- 模型拿到的**只有聚合结果**（明细检索例外：逐笔明细是答案本体，不是算术原料；代码同时附 sum/count 预聚合，模型引用哪个用哪个，禁止自己累加）。
- 所有聚合/占比/趋势/对比/方向由代码完成 —— 与 insight agent 同一条纪律（`02-analysis-rules.md` §6.1）。

### 5.2 回答必须带依据（证据卡）

每条含数字的回答，结构化输出引用它用的工具与值：

```json
{
  "answer": "今年 1-10 月水果共 ¥842.50，共 47 笔",
  "numbers": [
    { "value": "842.50", "source": "query_category_breakdown:sum" },
    { "value": "47",     "source": "query_category_breakdown:count" }
  ]
}
```

代码核对：`numbers[].value` 必须出现在工具返回值里，对不上 → 该数字剔除/整条重试。**这比旧版「正文数字白名单」误伤率低**（旧机制因 `'500.00'` vs `500` 格式差一位整条作废而废弃，`11-agent-harness.md` §6.1）—— 因为引用是结构化的，不是从自由文本里扒数字。

### 5.3 诚实降级

| 情况 | 行为 |
|---|---|
| 时间窗内无数据 / 笔数不足 | 明说，附「数据窗口 + 实际笔数」 |
| 同比基线不存在 | `hasYoYBaseline: false` + 指定文案 |
| 类目理解模糊 | 反问确认，不猜 |
| 问题超出能力范围 | 「这不是我的能力范围」+ 一句解释 |

### 5.4 「怎么省」V1 不答，引导到分析页（✅ 决策 6）

- 「怎么省」「该不该买」→ 回答「我不给省钱建议，分析页有详细建议」+ 引导入口。**不接护栏、不答建议** —— 这是范围决策，不是技术绕过：分析页的省钱建议已有完整护栏（刚性拦截 `findRigidViolation`、必需性消费 `essential-spend.js`），问数不再重复造一套。
- 「为什么涨」（归因）**可答**，但只陈述事实不评判：说「餐饮多花了 180」，不说「你花得太多了」（PRD v3 坑 #9，`22-roadmap.md` §7）。
- ⚠️ 若 V2 放开建议类，必须同步接上刚性/必需性护栏（`11-agent-harness.md` §6.3、`02-analysis-rules.md` §3）。

### 5.5 家庭账本（✅ 决策 7：只聚合不比较）

- 跟随当前账本（`personal` / `family`），复用 `resolveScope` 的权威口径：familyId 云端从 profile 反查，不信任前端；非成员拒绝（`02-analysis-rules.md` §12）。
- 家庭账单聚合在代码侧（family_bills 与 bills 同构 + familyId，`12-data-model.md` §1.3）。
- 答案中按需说明「以上为家庭账本」避免用户混淆。
- **成员间比较一律拒绝**（Q9）；prompt 铁律 + 测试用例双重保障。

### 5.6 时间表述口径与歧义澄清策略（✅ 决策 9、10，已确认）

用户说「最近」「这个月」「今年」时，Agent 必须有一套默认口径，且**答案强制标注**（证据卡附「按自然月 10 月计」）—— 否则答案与用户心里的口径对不上，信任崩塌。

| 表述 | 默认口径（✅ 已确认） |
|---|---|
| 「最近」 | **近 7 天**（滚动窗口），答案标注 |
| 「这个月 / 上个月」 | **自然月** |
| 「今年 / 去年」 | 自然年；「去年」优先理解为「去年同期」 |
| 「近 30 天」 | 滚动 30 天（与「本月」明确区分） |

**歧义澄清策略（✅ 已确认）**：
- **类目模糊**（「吃饭」是正餐还是含外卖）→ **反问确认**，列出候选（正餐 / 外卖 / 全部餐饮），不猜；

- **一轮澄清失败**（用户回复仍无法解析）→ 再问一次，仍失败 → 给示例问法引导。
- 多轮追问中的**条件继承**：时间窗、类目过滤可在追问中隐式继承；新增过滤条件需用户明确说出（「只看微信的」—— V1 不支持账户筛选，此例会引导回 Q5 边界）。

## 7. 技术架构草案

### 7.1 Agent 注册：复用现有 harness，不新造

现有 harness 已支持多 agent（`registerAgent`，`11-agent-harness.md` §1）。新增 **`ask` agent**：
- 注册在 **analysis-svc**（新 action `ask` + `pollAsk`，两段式见 §7.7）—— 不新建第 6 个云函数；查询纯函数进 shared 层，svc 仍是薄路由。膨胀后再拆。
- 复用 8 步调用链、13 个降级原因码、trace、脱敏、注入防护 —— 护栏与降级**零新造**，只新增「数字引用校验」（§5.2）与「能力边界声明」。
- `llm-client.js` 需新增流式能力（`stream:true` + 增量回调），改动集中在该文件；记账 agent 与 insight agent 保持 `stream:false` 不受影响。

### 7.2 工具集草案（6 个，带时间窗参数）

| 工具（草案名） | 用途 | 入参 | 出参要点 |
|---|---|---|---|
| `query_summary` | 时间窗概览 | `window`（锚点枚举，见下）+ 可选类目 | 总额/笔数/日均/最大单笔/中位数（代码算） |
| `query_category_breakdown` | 类目聚合 | `window` + 层级（1/2/3 级）+ 可选类目 + `topN` + `rankBy: amount\|count` | 金额 + 占比 + 笔数（**占比代码算**）；**双维度排名**（Q3） |
| `query_trend` | 月度趋势 | `window` + 可选类目 | 每月总额/笔数，缺失月补 0 |
| `query_compare` | 两区间对比 | `windowA` + `windowB` + 层级 + `align: true\|false` | 变化额/变化率/方向（代码判）/Top 驱动类目分解；**局部同期对齐**（Q2） |
| `query_bills` | 明细检索 | `window` + 排序 + `limit` + 备注关键词 | 逐笔 + **代码预聚合 sum/count**。⚠️ 无 account/source 入参（决策 8） |
| `query_recurring` | 跨月周期 | `window` + 可选类目 | 周期标签/次数/均价/稳定性（跨月纯函数，非 `calcRecurringPatterns`） |

**日期由代码锁定，模型只选锚点**：入参是枚举（`this_month` / `last_month` / `this_year` / `last_year_same` / `last_n_months:N` / `solar_festival:double_11` / `lunar_festival:spring_festival` + 年份 …），代码把锚点解析成日期并校验（from ≤ to、窗口 ≤ 上限）。模型不直接填日期字符串 —— 延续「日期由代码锁定」纪律，同时放开自由度。**农历锚点由代码调农历库解析（决策 5），模型不自己算农历日期**。

**参数越界必须报错回传模型**（沿用 `validateArgs` 纪律，`11-agent-harness.md` §5.2）—— 不静默夹住。

### 7.3 计算层：纯函数，不碰 LLM

新增 `shared/agent-harness/query-stats.js`（或扩展 `bill-stats.js`），全部可独立单测：
`calcWindowSummary` / `calcCategoryAgg` / `calcTrendSeries` / `calcCompare`（含方向判定）/ `calcTopBills` / `calcCrossMonthRecurring`。
对齐 PRD v3 M2 已规划的 `calcComparison` / `calcAnomalies` 等 —— **能合并的合并，禁止两套对比实现**（单一数据源原则）。

### 7.4 数据窗口与查询上限（两个已存在的静默失效点）

| 现状坑 | 出处 | 问数必须怎么处理 |
|---|---|---|
| `listBills` 的 `limit` 硬上限 100，月 >100 笔查询不全 | `12-data-model.md` §6.1 | 全走 `fetchAll` 分页，不撞单月 limit |
| `fetchAll` `hardCap = 2000` **静默截断**（不报错） | `12-data-model.md` §6.2 | 问数窗口上限设「笔数预算」：取数前先 `count`，超 2000 → 要么分页循环拉全（按月分片），要么**明确降级**「你的账单超过 X 笔，我按最近 N 笔统计」—— 绝不允许静默少算 |

**查询窗口上限（✅ 决策 14）：近 24 个月**，按月分片拉取；超出窗口的问题明确答复「我的统计范围是最近 24 个月，更早的账单暂不支持查询」，**不静默截断**。V1.1 再评估扩展到全历史。

### 7.5 多轮上下文：云端会话历史（2026-11-08 修订，替代原「前端携带」方案）

- **前端只带 `sessionId`**（新建会话由云端生成并随首答返回，前端存本地）；每轮「问题 + 回答摘要」由云端写入会话历史文档，组装 prompt 时读最近 N 轮。
- **文档**：`users/${openid}_askhistory_${sessionId}` —— **复用现有集合、不新建**（建表需管理员权限，`12-data-model.md` §1.1）；`REQUIRED_COLLECTIONS` 不变。
- **字段纪律与 job 文档同款**：顶层不得有 `month`（防 `listPendingInsightUsers` 每日扫描捞走，`12-data-model.md` §3.8）；读时校验 `userId === openid`（固定 _id 之外的双保险，§3.5）。
- **保留策略（✅ 决策 17）**：最近 10 个会话 × 每会话最多 20 轮；7 天未更新的会话惰性清理（挂在每次新 `ask` 上，无定时器）。
- **会话不绑定账本**：personal / family 切换由 `resolveScope` 逐问解析（§5.5），历史轮随轮记录当时的账本口径。
- **prompt 控制上下文预算**，超了截断最旧轮；**历史轮计入 `checkTokenBudget` 输入预算**。
- **为什么修订**：前端携带方案下，刷新/重进丢上下文、「我上次问过什么」类查询做不到、前端 payload 随会话增长、客户端可伪造历史（注入面更大）。云端历史只多一次 DB 读，换回：V1 即获得「刷新/重进凭本地 sessionId 续聊 + 上下文权威」；跨设备续聊与历史查询 UI 待 V1.1 会话列表 API 落地。

### 7.6 延迟与轮次预算（NFR 草案）

| 参数 | 草案值 | 理由 |
|---|---|---|
| `maxToolRounds` | 3 | 单问题通常 1 次规划 + 1-2 次工具 + 成文；比 insight 的 4 少一轮 |
| `budget.timeoutMs` | 15000 | 每轮 5000ms —— **不得低于 insight 的每轮 5000ms**（v3 血泪史：2500ms/轮必超时永远降级，`23-change-impact.md` §3.6） |
| 输出 `maxTokens` | 800 | 单回答比 5 条洞察短 |
| 目标延迟 | ≤ 10s P95 | 聊天场景，超 10s 用户会离开 |

- 若一次提问涉及多个独立数字（如「三类支出各多少」），优先**一次工具调用拿全**，避免多轮往返 —— prompt 里明确「能一次问完的工具调用不要拆多次」。

### 7.7 流式输出（✅ 决策 16：路线 B —— 两段式 + 增量落库）

**架构约束（实测）**：
- 小程序 `callFunction` 是**一次性请求/响应**，云端不能把 LLM 的 SSE 直接转发给前端 —— 「流式」只能靠**两段式 + 主动获取**。
- 当前 harness 固定 `stream:false`（`llm-client.js:82`），无任何流式能力。
- 项目唯一长任务先例是 ASR：`startRecognize` 立即返回 `jobId`，后台跑识别，前端每 1.2s 轮询 `pollResult`；任务状态存在**实例内存** `JOBS` Map（`asr-svc/index.js:60`）。

**选定路线 B：两段式 + 增量落库**

```
前端 ──ask {question, sessionId}──→ analysis-svc
       ←── {jobId} 立即返回（毫秒级）
后端后台：工具循环 → 逐段生成答案（stream:true）→ 节流写 job 文档（每 300-500ms 或每 ~50 token）
前端 ──pollAsk {jobId}──→ 每 500ms 读 job 文档 → 增量渲染
       ←── {status, answerChunks, done, numbers}
完成后：job 文档删除、本轮问答摘要写入会话历史（§7.5）；失败 → {status:'error', reason}
```

**关键实现决策**：

| 项 | 决策 | 理由 |
|---|---|---|
| job 存储位置 | **复用 `users` 集合**，文档 `_id = ${openid}_askjob_${jobId}` | 避免新集合手工创建（云开发建表需管理员权限，`12-data-model.md` §1.1）+ `REQUIRED_COLLECTIONS` 连动。与 `${openid}_profile` / `${openid}_insight` 同模式 |
| 顶层字段纪律 | **不得有顶层 `month`**（防被 `listPendingInsightUsers` 的 `where({month})` 捞进每日分析扫描 —— 与家庭 insight 同一条坑） | `12-data-model.md` §3.8 |
| 清理 | 完成/失败后立即 `remove`；另在每次新 `ask` 时惰性清理该用户 1 小时前的残留 job 文档 | 无需新增定时器 |
| 增量节流 | 每 300-500ms 或每 ~50 token 写一次，**不逐 token 写** | DB 写成本可控 |
| 越权 | `pollAsk` 校验 job 文档 `userId === openid`，不匹配返回空（同 insight 读时校验） | `02-analysis-rules.md` §9.2 |
| LLM 流式 | `llm-client.js` 新增 `chatWithToolsStream`（或给 `chatWithTools` 加 `onChunk` 回调）；DeepSeek 支持 `stream:true` | 改动面集中在 `llm-client.js` |
| 流式与工具轮次 | **工具调用轮不流式**（只流式最终成文轮） | 工具参数是 JSON，流式无意义且干扰解析 |

> ⚠️ **前端渲染必须分段**：先出已完成的句子，未完成部分显示光标；**数字证据卡在最终答案到达后才出现**（避免半截数字被误读）。流式期间回答文字中的数字可能尚未完成 —— 渲染层对未完成的 `numbers` 一律不展示。

**兜底**：流式失败（job 文档缺失/超时）→ 前端退化为「直接等待完整答案」，`ask` 的第二段仍会落最终结果；假流式打字机仅作为最后手段。

## 13. 验收标准草案

- [ ] 「今年买水果花了多少」→ 数字与手工核对一致，证据卡显示窗口、笔数与口径
- [ ] 「相比去年哪类涨最多」→ 有基线时数字正确；无基线时 `hasYoYBaseline: false`，**零编造**
- [ ] 「本月前 10 天 vs 上月前 10 天」→ 局部同期对齐，变化率基于等长窗口，答案标注对齐口径
- [ ] 「哪类笔数最多」与「哪类花最多」→ 排名维度区分正确，笔数排名不会被说成金额排名
- [ ] 「去年春节花了多少」→ 农历解析日期正确（闰月、跨年边界用例），窗口 = **除夕至正月十五**；「双11」→ **11.1-11.11**；「618」→ **6.1-6.18**；「双12」→ **12.1-12.12**，证据卡均标注口径
- [ ] 预置高频问题气泡点击 → 走同一问答管道，答案与手工输入完全一致
- [ ] 「为什么这个月花多了」→ 驱动类目与金额与 `calcCompare` 输出一致；文案无评判性措辞
- [ ] 「怎么省」→ 引导分析页，不给建议；「谁记的账最多」→ 拒绝，只聚合不比较
- [ ] 模型输出与工具返回值不符的数字 → 被引用校验剔除/重试
- [ ] 窗口内无数据 → 明确说明，不编造；类目理解模糊 → 反问，不猜
- [ ] 多轮追问：时间窗/类目过滤隐式继承正确；不支持的条件（账户筛选）明确拒绝；上下文取自云端会话历史（前端只带 sessionId）
- [ ] 超 2000 笔 → 拉全或明确降级声明，**无静默少算**
- [ ] 参数越界 → 报错回传，模型自我纠正
- [ ] LLM 不可用 → 「AI 暂不可用」，不出任何假数字
- [ ] 家庭账本：非成员拒绝；答案标注账本归属
- [ ] 流式：首段文字在 3s 内出现；数字证据卡在最终答案到达后才显示；流式中途刷新页面 → 可凭 jobId 续取或明确提示重试
- [ ] job / 会话历史文档：job 完成后删除、残留 1 小时懒清理生效；会话历史读时校验 userId、顶层无 `month`（不被每日分析扫描捞走）、保留策略生效（10 会话 × 20 轮、7 天惰性清理）
- [ ] 刷新/重进聊天页凭本地 sessionId 续聊（多轮上下文不丢）；历史轮计入 token 预算熔断
- [ ] 第 51 次提问 → 明确提示「今日问数次数已达上限」
- [ ] 超 24 个月窗口的问题 → 明确答复「统计范围最近 24 个月」，不静默截断
- [ ] 日预算熔断生效
