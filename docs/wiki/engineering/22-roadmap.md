## 2. PRD v3 要做的五件事

### F2 对比分析（核心）

| 需求 | 内容 | 前置 |
|---|---|---|
| 分类目环比 | 每个一级类目本月 vs 上月，输出变化额与变化率 | 现有能力可扩展 |
| 驱动因素分解 | 总变化额按类目拆解，标注 Top 驱动类目 | 新统计函数 |
| **同比** | 本月 vs 去年同月 | **窗口 6 → 13 个月** |

**同比的诚实降级**（PRD §FR2.2，不可妥协）：
去年同月无账单或有效笔数 < 3 笔 → 返回 `hasYoYBaseline: false`，
前端显示「记账未满一年，明年此时可看同比」。
**禁止用其他基线冒充同比。**

### F3 周期性支出

三层含义**全部实现**（2026-10-24 与产品负责人定稿）：

| 层 | 内容 |
|---|---|
| FR3.1 识别（增强） | 周期标签、次数、单次均价、月总额 + **金额稳定性**（`cv()`：<0.2 稳定 / ≥0.5 波动大） |
| FR3.2 频率画像（新增） | 一级类目的平均记账间隔、单次均价、月次数 + **消费模式标签**（规则判定，非模型判定） |
| FR3.3 补记分析（新增） | 补记率、集中补记日；补记率 > 40% 时日均文案追加「按记账日计算日均可能失真」 |

### F4 异常信号（新增）

| 信号 | 判定规则 |
|---|---|
| 单笔离群 | 某类目内单笔 > 该类目中位数 × **3**，且类目笔数 ≥ 4 |
| 类目突增 | 分类目环比涨幅 ≥ **50%** 且变化额 ≥ **100 元** |
| 类目突降 | 分类目环比降幅 ≥ **50%** 且变化额 ≥ **100 元** |

- 每次分析**最多 3 条**，按金额影响排序。
- 环比基线不存在（上月无数据）时，突增/突降**不判定**；单笔离群不受影响。

### F5 消费节奏画像（新增）

工作日 vs 周末、上/中/下旬分布、月末突击（下旬占比 ≥ 45% 且笔数 ≥ 5）。

> ⚠️ **只进 `insights`，不进 `savings`** ——
> 不给「少在月末花钱」这类空洞建议（PRD §F5 末句）。

### F6 结构化输出

`insights`（字符串数组）**保持不变**，并行新增 `structuredInsights`：

```json
{
  "structuredInsights": [
    { "type": "anomaly", "text": "...", "evidence": "get_anomalies: outlier/购物/480", "severity": "warn" }
  ],
  "insights": ["..."],
  "schemaVersion": 3
}
```

- `type` 与 `evidence` 由**代码生成或护栏校验**，模型只填 `text` 与 `severity`。
- **双写必须同源** —— `structuredInsights[].text` 由 `insights` 生成，
  **禁止两条生成路径**（否则双写期数据不一致，见 PRD §十风险表）。

## 4. 非功能需求（实施时要盯的硬数字）

| 项 | 要求 |
|---|---|
| 单次分析耗时 | ≤ **15 秒**（原 10 秒；数据翻倍 + 轮次 3→4） |
| `dailyInsight` 批量 | 40 秒硬预算**不变**；单用户耗时重测后自动收缩每批人数（现有时间预算机制，无需改代码） |
| Token 预算 | 输出 1400 → **2000**，总 1800 → **2400** |
| 工具规模 | 11 → ≤ **15** 个；轮次 3 → **4**；对比类维度**合并为 `get_comparison` 单工具**，禁止碎片化 |
| Prompt | 长度不超过现版 **110%** |
| 可回滚 | `LLM_ENABLED=false` 一键回规则版；`schemaVersion` 支持前端按版本分支 |

> ⚠️ **别把每轮预算调回去**。v3 血泪史：总预算 10s ÷ 4 轮 = 每轮 2500ms，
> 对 function-calling **太紧** → 每轮必超时 → **永远走降级**。

## 5. 实施阶段（PRD §九）

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| **M1** 数据层 | 窗口 13 个月、normalize 保留 `createTime` | 单测通过，拉取耗时实测记录 |
| **M2** 统计层 | `calcComparison` / `calcAnomalies` / `calcRhythm` / `calcRecordHabits` / `calcCategoryFrequency` + `calcRecurringPatterns` 增强 | 全部单测 |
| **M3** 工具与 Prompt | 新工具注册、`get_comparison` 合并、铁律表更新 + prompt 精简 | 本地 harness 冒烟，工具调对率抽检 |
| **M4** Schema 与护栏 | 双写输出、对账扩展、fallback 模板补齐 | 验收标准「后端」全绿 |
| **M5** 预算重测与灰度 | 耗时/token 实测调参，小流量验证 | NFR 达标后全量 |
| **M6** 前端分区渲染 | 分析页五分区（**独立排期**） | 前端验收项通过 |

> ⚠️ **M2 是纯计算层** —— 不碰 LLM、不碰前端，可独立单测。
> 这是整个 PRD 里**风险最低、最该先做**的一段。
> 参考现有做法：`bill-stats.js` 是纯计算不碰 LLM，`tools/index.js` 只做声明+执行。

## 7. 实施时会踩的坑（已提前识别）

| # | 坑 | 说明 |
|---|---|---|
| 1 | **`saveInsight` 字段白名单** | 新字段不加进去就不落库 → 「当次有、刷新后消失」的时好时坏 |
| 2 | **`normalizeBills` 丢弃 `createTime`** | 补记分析完全依赖它，M1 必须先修 |
| 3 | **工具依赖校验会误杀新维度** | 新维度的 `tools` 列表没加新工具 → 结论被剔除（`agent-harness/index.js:382` 的 `CONCLUSION_REQUIRES`） |
| 4 | **`OUTPUT_SCHEMA` 校验不严** | 只认 `properties`/`required`，而 insight 用 `fields`/`requiredFields` → 类型写错也通过，**别指望它兜住** |
| 5 | **`calcRecurringPatterns` 检不出月付订阅** | 入参是**单月**数组 → 架构上就检不出跨月。周期需求不能想当然复用它 |
| 6 | **同比拉取量翻倍 → 耗时超限** | 预案：同比基线改为独立轻查询（仅去年同月聚合值） |
| 7 | **Prompt 变长稀释注意力** | 工具漏调、规则违反 → 分节精简 + 抽检调对率 |
| 8 | **双写不一致** | `structuredInsights[].text` 必须由 `insights` 同源生成 |
| 9 | **文案冒犯用户** | 「异常」易被理解为「乱花钱」→ 基调「陈述事实 + 提供视角」，**禁用评判性措辞** |
| 10 | **新维度触发刚性护栏误伤** | 异常信号只作「事实陈述」，**不作节省建议** → 不进 `savings` |

> 这 10 条与 `20-pitfalls.md` 有重叠 —— **动手前两页都要读**。

## 8. 验收标准摘要（PRD §八）

实施完成后必须逐条核对：

- [ ] 账单跨度 ≥ 13 个月的用户，同比结果与手工核算一致
- [ ] 跨度 < 13 个月 → `hasYoYBaseline: false`，**不出现编造的同比数字**
- [ ] 分类目环比 + 驱动分解：构造用例（购物 +410、餐饮 +180、交通 −78），归因数字与 stats 一致
- [ ] 异常检测三项规则各有单测（**含阈值边界**：恰好 3 倍中位数、恰好 50% 涨幅）
- [ ] 补记判定：差 1 天**不计**补记、差 2 天**计**补记
- [ ] 频率画像：笔数 < 3 的类目**不出画像**
- [ ] 护栏：构造模型输出编造数字（如同比写 300%），`structuredInsights` 对账拦截生效
- [ ] 降级：`LLM_ENABLED=false` 时新维度模板结论齐全且数字正确
- [ ] 双写：`insights` 与 `structuredInsights[].text` 一一对应，`schemaVersion: 3`
- [ ] 旧已落库文档（无新字段）经 `categoryBreakdown` 读取，前端渲染不报错
- [ ] 13 个月、单月 ≤ 200 笔规模下 `computeInsight` 全程 ≤ 15 秒（P95）

> ⚠️ 「含阈值边界」的单测最容易漏 —— 恰好 3 倍、恰好 50% 这类**等号边界**
> 是规则实现最常出错的地方（`>` vs `>=`）。
