# 20 踩坑清单

> 覆盖：本项目已验证的故障模式 —— 每条含**现象 → 根因 → 修法 → 现在的防线**。
>
> 权威实现在源码；本文的行号只作**佐证**，动手前 grep 复核。
> 判定标准：**必须能复现**。没复现过的推测不写进来。

## 1. 云函数找不到 shared 模块

**现象**：本地 `require` 正常、测试全绿，部署后报
`Cannot find module '/var/shared/...'`。

**根因**：「上传并部署：云端安装依赖」**不上传本地 `node_modules`**。
以下两种放法云端都找不到：
- 复制到 `node_modules/shared`（云端安装依赖时该目录不存在）
- 仓库根的 `__dirname/../shared`（**不在打包范围内**）

**修法**：shared 必须是**函数目录内的普通子目录** —— `cloudfunctions/<svc>/shared/`。
`npm run prepare:cf` 负责复制。

**防线**：`analysis-svc/index.js:37-58` 的 `loadShared()` 按「云端可达性」排序候选路径，
全部失败时**直接抛错并提示跑 `prepare:cf`**，不静默降级。

> **本地全绿 ≠ 云端能跑。**

## 2. 云端没有全局 `fetch`

**现象**：`ReferenceError: fetch is not defined` —— 只在云端发生，本地永远复现不了。

**根因**：云函数运行时是 `Nodejs18.15` + **CommonJS**。
Node 18 只在 ESM 上下文把 `fetch` 注入 `globalThis`，本项目全用 `require` → 拿不到。
本地 Node 22 有全局 `fetch` → **本地全绿、云端必然失败**。

**修法**：云端发 HTTP 一律用 `shared/util/http-client.js` 的 `postJson()`。
**禁止在云函数里写 `fetch(...)`**。

**防线**：测试必须 mock 同一个东西 —— 注入 `httpClient.__setImpl()`，
且要注入**云函数实际加载的副本** `cloudfunctions/<svc>/shared/util/http-client.js`（不是源文件）。
验证方法：`delete global.fetch;` 后仍能正常发请求。

## 3. shared 多副本导致「改了没生效」

**现象**：改了代码，部署了，行为还是旧的；报错信息**指错了方向**
（提示「确认两端来自同一版本」，实际是副本没同步）。

**根因**：shared 被**复制**进 5 个云函数目录 → 同一模块存在多份副本。
只改源 `cloudfunctions/shared/` 而没跑 `prepare:cf` → 副本停在旧版本。

**修法**：改 shared 后必跑 `npm run prepare:cf`。

**防线**：preflight 做了**内容级守卫**（逐文件 sha1），不是只查存在性。
⚠️ **存在性检查对漂移失灵** —— 旧副本文件也都在，路径也正确。

## 4. 版本戳不同步，报错方向是错的

**现象**：真机日志出现 `[cloud] 版本不一致/版本过旧` 警告，功能照常跑。
（2026-11-03 之前是弹「云端与本地代码版本不一致」并阻断调用。）

**根因**：`CODE_VERSION`（云端 `shared/util/constants.js`）与
`EXPECTED_CODE_VERSION`（前端 `miniprogram/utils/cloud.js`）是两处独立常量。

**修法**：改云函数代码必须四步走：

| # | 动作 | 自动化 |
|---|------|--------|
| 1 | `shared/util/constants.js` 的 `CODE_VERSION` +1 | ✅ preflight |
| 2 | 同步 `miniprogram/utils/cloud.js` 的 `EXPECTED_CODE_VERSION` | ✅ preflight |
| 3 | `npm run prepare:cf` | ✅ 有脚本 |
| 4 | 开发者工具右键云函数 →「上传并部署：云端安装依赖」 | ❌ **只能人工** |

**防线**：preflight 校验两端版本戳一致（`:753`）；前端对账 2026-11-03 起
**只警告不阻断**（原「业务错误判断之前 throw」已废除 —— 云端部署会连带
把已发布线上版的每次调用挡掉，窗口随审核节奏不可控，见
`tech/10-architecture.md` §7.2）；`action==='diag'` 跳过对账（诊断要能穿透）。

## 5. 云函数 timeout 可能不生效

**现象**：真机上 timeout 写 25s，实际按 3s 执行。

**根因**：官方注明**云函数配置只对 `$LATEST` 生效**。

**修法**：确认部署的是 `$LATEST`；timeout 要匹配各自的耗时结构：

| 云函数 | 结构 | 最低 timeout |
|--------|------|------|
| `bill-svc` | 单次 LLM（~2.2s） | ≥10s |
| `analysis-svc` | 3~4 轮工具往返 + 数据库 + 冷启动 | ≥11s（建议 30~40） |

analysis-svc 的预算算法（**别照抄简版**）：
```
perRoundSec = ceil(max(800, ANALYSIS_LLM_TIMEOUT_MS / ANALYSIS_MAX_TOOL_ROUNDS) / 1000)
needSec     = perRoundSec + 3（数据处理）+ 5（冷启动）
```
`chatWithTools` 把预算**分摊到每轮**（单轮 ~2.7s 而非 8s）；
**冷启动不计入 LLM 预算**却实 eats 总时长。

## 6. 删代码留下残留引用

**现象**：每次请求都抛 `ReferenceError` —— 但 `node --check` 查不出来。

**根因**：删掉 `AbortController` 后，`finally { clearTimeout(timer) }` 仍引用已删变量。
**语法合法，运行期才炸。**

**修法**：删变量必须搜一遍所有引用（**含 finally / catch**）。

**防线**：全量测试覆盖真实调用路径，不只做语法检查。

## 7. 金额上限散在 4 处、3 种单位 ⚠️

**现象**：改金额上限时「改了数字但行为没变」；或两处上限不一致导致诡异行为。

**根因**：同一个「单笔金额上限」概念散在多处，**单位还不同**：

| 位置 | 值 | 单位 | 作用 |
|---|---|---|---|
| `shared/util/constants.js:100` | 50000 | 元 | `GUARDRAIL.MAX_AMOUNT_YUAN`，超限强制人工确认 |
| `shared/util/money.js:100` | 50000 | 元 | `isReasonableAmount()` 上限 |
| `shared/rules/asr-parse.js:116` | 100000 | 元 | `arabic_bare` 粗筛上限（**比上面宽一倍**） |
| `shared/util/money.js` | — | 分 | 内部一律整数分 |

**修法**：改上限时 grep 全仓，逐个确认；注意 `arabic_bare` 的粗筛比真实上限宽。

**防线**：`tools/preflight.js` 校验 `constants.js` 与前端版本戳一致。

## 8. ⚠️「12 万」被解析成 12 元（不是「解析不出来」）

**现象**：说「买了12万的车」→ 记成 **12 元**，而且 `certain: true`（**看起来很确定**）。

**根因**：`arabic_bare` 的正则 `/(\d+(?:\.\d{1,2})?)(?![\d.%])/`（`asr-parse.js:37`）
在「12万」上匹配到 `12`；否定前瞻 `(? ![\d.%])` 的排除集里**没有「万」** → 数字被截取，
「万」字静默丢弃。

**实测**：
```
extractAmount("买了12万的车") = { amountCent: 1200, certain: true, pattern: "arabic_bare" }
```
对比：`cnToNumber("十二万") = 120000` ✅ —— **中文「万」能解析，阿拉伯「万」不能**。
中文模式 `chinese_bare` 的字符集 `[零一二三四五六七八九十百千两]{2,}` **同样不含「万」**。

**修法**（待实施）：给 `arabic_bare` 补「万/亿」单位支持，
或让否定前瞻排除量词字 `[万億亿]`；同时 `chinese_bare` 字符集补「万」。

> ⚠️ **比「解析不出来」更危险**：解析不出来时 `amountCent: null` → 走人工确认；
> 现在这种情况给出**错的确定值** → 直接落库，用户完全看不出错在哪。
> 改金额上限/数量级解析时必须一起处理，否则**需求实际没生效**。

## 9. ⚠️ 两个同名 `yuanToCent`，契约完全不同

**现象**：`yuanToCent('120.00')` 返回 `null` 而不是 `12000` —— 但代码「看起来」是对的。

**根因**：全项目有两个同名函数，**签名不同**：

| 位置 | 入参 | 返回 | 实现 |
|---|---|---|---|
| `shared/util/money.js:10` | **number** | `number\|null` | `Math.round(yuan * 100)`（**浮点**） |
| `miniprogram/utils/format.js:91` | **string** | `number\|null` | **按字符串逐位解析**，全程整数运算 |

云端用前者，前端用后者。传错类型 → `null`（`money.js:11` 的 `typeof !== 'number'` 守卫）。

**修法**：**云端用 `money.js` 的（传数字），前端用 `format.js` 的（传字符串）。**
前端解析金额一律走 `format.js` 的版本 —— `detail.js:260` 是正确范例。

**防线**：`tools/__tests__/money-format.test.js` 锁住前端契约；
`tools/check-frontend.js:472` 断言明细页用的是字符串解析版本。

## 10. 浮点乘 100 会少一分

**现象**：金额差 1 分，用户完全看不出错在哪。

**根因**：`parseFloat('8.115') * 100 = 811.4999999999999` → `Math.round` → **811**，正确答案是 **812**。

**修法**：按字符串逐位解析 —— 整数部分 ×100 + 小数前两位 + 第三位四舍五入（`format.js:91-115`）。
全程整数运算，无浮点。

**防线**：`money-format.test.js:81` 断言 `yuanToCent('8.115') === 812`。

> ⚠️ 云端 `money.js` 的 `yuanToCent` **仍是浮点**（`Math.round(yuan*100)`）——
> 它只接受已解析好的 number，风险低于前端，但**不是同一个保证**。

## 11. 金额字段双名：`amount` vs `amountCent`

**现象**：编辑面板回填后金额显示 **0**，点保存报「请输入有效金额」，**全程零报错**。

**根因**：`groupByDate` 里 `amount` 是**展示用字符串** `"¥120.50"`，
`amountCent` 才是原始分 `12050`。回填传了 `bill.amount` →
`Number("¥120.50")` = **NaN** → 面板显示 0。

**修法**：回填用 `yuanInput(bill.amountCent)`（`detail.js:175` 是正确范例）。

**防线**：`tools/__tests__/edit-bill.test.js` + `check-frontend.js` 覆盖编辑面板。

> **教训**：展示值与计算值**不要共名字段**。同一份数据存两个字段、名字又长得像 → 早晚会传错。

## 12. 静默降级：`|| []` 把错误吞掉

**现象**：建议整块消失，**没有任何报错**。

**根因**：`Array.isArray` 判定失败时用 `|| []` 兜底 → 建议被无声清空成空数组。

**修法**：不要 `|| []`，直接 `throw` 让错误暴露。

**防线**：分析链路的降级必须**显式标记**（如 `meta.savingsSource`），
并区分「故障」与「护栏正常工作」两档。

## 13. 刚性支出被当成可省 → 数学全对结论全错

**现象**：建议「学费省 30%」「房租省 1050」—— 算得一点没错，但**建议本身荒谬**。

**根因**：刚性类目（房租/学费/药品/物业/保费/宽带/奶粉）进了建议池。
`util/category-compressibility.js` 三档：`rigid`（**禁止出现在任何建议里**）/
`semi`（可提但克制）/ `flexible`（真正空间）。

**修法**：**顺序必须是：先剔刚性 → 再判笔数 → 最后截断。**

**防线**：刚性白名单硬拦截 —— 数值对账查不出「根本不该提这个类目」，
必须有一道独立的**白名单守卫**。

## 14. 备注关键词被 LLM 总结时丢掉 → 刚性判定失效

**现象**：说「孩子学费3200」→ 备注被总结成「教育支出」→ 学费被当成可省项。

**根因**：LLM 总结时**丢了关键词**，刚性判定依赖备注关键词 → 失效。

**修法**：关键词表集中在 `shared/util/note-keywords.js`（**单一数据源**，
被 compressibility / essential-spend / note-summary 三处共用）。
检测到丢词就**退回用户原话全文**，不拼接（拼接出来像机器拼的故障）。

**防线**：`shared/util/note-summary.js` 的 `buildNote({asrText, llmNote})` 三条路径：
① 总结可用且没丢关键词 → 用总结 ② 丢了关键词 → 原话全文 ③ 无摘要 → 原话全文。

> ⚠️ **兜底用原文而非规则提炼**：模型没帮上忙时，信息完整优先于简洁。
> ⚠️ 兜底路径备注里**带金额**（如「买菜100」）—— 这是需求明确要求的取舍，
> 明细页金额是独立字段，不参与计算。

## 15. 样本量门槛随版本变过，别照抄旧文档

**现象**：按旧文档说「`MIN_SAVING_BILLS = 3`」去改代码 → **零命中**，以为写错了。

**根因**：该常量**在 v3 中已随 `calcSavingsPotential` 一并删除**。
现在 v3 的建议是否给出**完全由模型判断**，规则层不拦。
现存最接近的常量是 `bill-stats.js:285` 的 `MIN_OCCURRENCES = 3` ——
但那是**周期消费检测**用的，不是节省门槛。

**修法**：动手前先 grep 确认常量是否还存在。
**代码是权威，文档是快照** —— 这类「文档写了但代码已删」的情况正是 Wiki 坐标会失效的原因。

**防线**：仍然成立的通用原则 ——
任何「按比例估算省多少」都隐含样本量假设，
**笔数不足时应明说「数据还不够」**，而不是硬给建议。
空建议卡片同样有害 —— 无建议时必须说明原因，
并区分「数据还不够」vs「本月以刚性支出为主」。

> ⚠️ **样本量门槛要分场景**：「按比例估算省多少」需样本；
> 「这一笔值不值得提」**不需要** —— 备注本身就是判断依据。
> ⚠️ v3 移除规则层门槛 ≠ 「小样本可以随便建议」——
> 护栏仍有**刚性白名单**与**结论依据校验**两道。

## 16. WXML 数据绑定断裂 → 柱子只剩 4rpx

**现象**：趋势图的柱子几乎看不见，**布局完全正常**（不报错）。

**防线**：契约测试**真解析 WXML** 并断言**值不是 undefined**
（只查 key 会漏 —— key 在但值是 undefined 一样炸）。

## 17. 布局塌陷到 0 高度

**现象**：滚动区被压扁，内容看不见。

**根因**：`max-height` 单独存在 + 滚动区 `flex:1; min-height:0` → 可被压到 **0 高度**。

**修法**：① 滚动区必须有 `min-height` 硬下限 ② flex 分配高度时父容器要有确定 `height`
③ 同级兄弟区也要限高。

**防线**：用真实浏览器量（Playwright 复刻 WXML+WXSS，读 `getBoundingClientRect`）——
**纯读 CSS 看不出塌陷**。

## 18. 虚拟分组被当成类目 → 云端拒绝

**现象**：自定义类目组的账单，云端处理时报「找不到类目」。

**根因**：`custom_{topId}`（`customGroup=true`）是**展示容器**，不是类目。

## 19. 定时触发器 event 结构 ≠ action 分发

> ✅ **已修复（2026-10-31，版本 `20261031-02`）** —— 修复前定时分析**从未真正执行过**。

**现象**：定时任务每天 0 点跑，但**什么都没发生**，无报错。

**根因**：官方定时触发器下发的 event 是
`{ Type:'Timer', TriggerName:'dailyInsight', Time:'...', Message:'' }` ——
**没有 `action` 字段**。而 `analysis-svc/index.js` 的分发认的是 `event.action`
→ 解构出 `undefined` → `switch` 落 `default` → 返回「未知操作: undefined」。

**实测（修复前）**：喂官方真实 event → `ok=false`、落库 0 条；
喂 `{action:'dailyInsight'}` → `ok=true`、processed=1。

**根因之二**：现有测试全部**手工构造** `{action:'dailyInsight'}`，
绕过了「平台怎么下发 event」这一层 → **测试全绿但功能是死的**。

**修法**：在入口做**分发归一** —— `normalizeEvent()` 识别 `event.Type === 'Timer'`
→ 映射成 `action='dailyInsight'`；`TriggerName` 对不上则拒绝（不误跑批量任务）。

**防线**：
- 测试用**官方真实 event 结构**喂（`daily-insight.test.js` 的「官方定时触发器事件结构」段）
- `Timer` 的 `payload` **不透传** —— 防外部构造 `{Type:'Timer', payload:{month,cursor}}` 注入参数
- 下游 `isTriggerSource()` 仍校验 `SOURCE === 'wx_trigger'`（**外部无法伪造 SOURCE**）

> ⚠️ **cron 本身是对的**：`0 0 0 * * * *` 是 7 段 = 每天 0 点（UTC+8）。别去改 cron。

## 20. 云函数时区是 UTC+0，触发器 cron 是 UTC+8

> ✅ **已修复（2026-10-31，版本 `20261031-02`）**

**现象**：定时任务在**每月 1 号**分析的是**上个月**的数据。

**根因**：云函数运行时时区 UTC+0，触发器 cron 规则时区 UTC+8。
`dailyInsight` 用 `dateUtil.toMonthStr(new Date())` 取月份 → 走本地时区 → **差 8 小时**。

**修法**：新增 `shared/util/date.js` 的 `toMonthStrCST()` / `toDateStrCST()` ——
**固定 +8 小时偏移**，不依赖运行时 TZ，也不依赖控制台配没配 `TZ` 环境变量。
`dailyInsight` 改用它，**且用触发时刻（`event.Time`）而非 `new Date()`**。

> ⚠️ **没有改 `toMonthStr`** —— 它被 5 个云函数共用
> （`db/index.js` 区间查询、`user-svc` 笔数统计等），那些路径的语义是
> 「服务器本地时区的月份」，改口径会波及一片。
> **只有定时任务需要「东八区自然月」这个明确口径。**

**防线**：
- `npm run test:tz-utc` —— **在 `TZ=UTC` 下也跑一遍全部定时测试**
- 测试断言的是**调用点**（`dailyInsight` 算出的月份），不只是函数本身

> ⚠️ **本地开发机是 `Asia/Shanghai`（UTC+8）**，恰好等于正确的东八区 →
> 「退回本地时区」这种错误在本地**测不出来**。
> **必须在 `TZ=UTC` 下测**才能暴露 —— 这是本地全绿、云端失败的一个新变种。

## 20b. ⚠️ `test()` 不 await → 所有断言都没跑，却全绿通过

> ✅ **已修复（2026-10-31）** —— 这个缺陷让 §19 的 bug 长期藏着。

**现象**：测试日志里有红字（某条断言失败），但结尾仍打印「N 通过 / 0 失败」，
**退出码 0**，CI 全绿。

**根因**：`test()` 是同步的 `try { fn(); } catch {}`。
对 `async` 函数，`fn()` 返回 Promise，**不会同步抛错** →
断言失败变成**未捕获的 Promise 拒绝** → `try/catch` 根本抓不到。

**真实表现（2026-10-31 实测）**：
加了 5 个 async 断言，其中 3 个真的失败、日志有红字，
但结尾仍报「7 通过 / 0 失败」并 `exit 0`。
「定时触发器进不了 dailyInsight」这个 bug 就这样被掩盖了很久。

**修法**（三处，缺一不可）：
1. `test()` 改成 `async` 并 `await fn()`
2. 加 `process.on('unhandledRejection')` 监听 → 记为失败
3. ⚠️ **用 `process.exitCode` 而不是 `process.exit()`** ——
   `process.exit()` 是**立即**终止进程，未处理的拒绝根本没机会触发 → 缺陷被吞。
   且监听器里必须**直接设 `process.exitCode = 1`**（只 `failed++` 没用，
   因为 `main()` 末尾已经设过 exitCode）。

**防线**：注入 bug 验证 —— 把 `await fn()` 改回 `fn()`，退出码必须变成 1。

> **通用教训**：「所有检查都通过」不等于「检查是对的」。
> **守卫本身也要用「注入 bug」的方式验证。**

## 20c. ⚠️ mock 不过滤条件 → 断言测的是 mock 不是代码

> ✅ **已修复（2026-10-31）**

**现象**：「跨月结果不算本月已分析」这条断言**永远不成立**，
但因为 §20b 的 `test()` 没 await，失败被吞 → 报「全部通过」。

**根因**：mock 的 `where()` **完全无视查询条件**，无条件返回全部文档：

```js
// ❌ 修复前
where() { return { limit() {...}, async get() { return { data: USER_DOCS.slice() }; } }; }
```

于是 9 月的分析结果也被当成 10 月的 —— **mock 不忠实于云开发语义**。

**修法**：
- `userCol.where(cond)` 真的按条件过滤
- `billCol` 的 `command.gte(x).and(lte(y))` 还原成可比较的 `{min,max}`，真的过滤日期区间
- `delFlag: false` 的语义是「未删除」（字段缺失视为未删除）

**防线**：注入 bug 验证 —— 断言必须能真的失败。

> **通用教训**：**mock 不忠实，测的就不是代码。**
> 写 mock 时要问「云开发真实行为是什么」，而不是「怎么让测试过」。

## 21. 触发器部署是两步，不是一步

**现象**：改了 `config.json` 的 cron，触发时间没变。

**根因**：「更新触发器文件」与「上传触发器」是**两个不同概念**：
前者让云函数端的触发器文件更新，后者让触发器开始生效执行。
只做前者 → 云端跑的还是旧触发器内容。

**修法**：改 `config.json` 后 →
① 右键 `config.json`「云函数增量上传：更新文件」→ ② 右键 `config.json`「上传触发器」。

**附带约束**：`config.json` **不能有注释**（云开发不解析注释）；数组最后一项不能有逗号；
cron 必须 7 段，不能多也不能少。

→ **补页要补判断，不是补坐标**。

## 56. 跨副本的 mock 注入失效

**现象**：明明注入了 mock，落库却仍被跳过。

**根因**：shared 是**复制**的 → 同一个模块有多份副本；
只存模块级变量 → 测试注入的是 A 副本，被测代码用的是 B 副本。

**修法**：注入写 `globalThis`（`shared/db/sdk.js:95-106` 的 `__injectSdk`）。

**防线**：验证方法 —— `delete global.fetch;` 后仍能正常发请求。

---

## 57. `preflight` 的副本漂移守卫曾只查「存在性」

**现象**：改了 shared，preflight 说副本都在，但部署后是旧代码。

**根因**：只查文件存在 → 旧副本文件也在、路径也对。

**修法**：改用**内容级守卫**（逐文件 sha1）。

**教训**：**存在性检查对漂移失灵。** 守卫要看**内容**，不看**存在**。

## 58. `fetch` 的 `AbortController` 删了但 `finally` 还在用

见 §6（同源）。补充：**删代码要搜一遍所有引用**（含 finally/catch）。

## 59. 前端 `wxss` 的 `min-height: 0` 恰是原始 bug

**现象**：守卫跑绿但布局仍塌。

**根因**：守卫的正则断言「值 > 0」被写成「值存在」。

**修法**：**守卫的正则要断言「值 > 0」** —— `min-height: 0` 恰是原始 bug 的形态。

## 60. `arr` 数组被 `|| []` 兜底后静默清空

见 §12 / §26（同源的两个表现）。统一记法：**不要用 `|| []` 兜底，直接 `throw`**。

## 61. `users` 集合混存：家庭 insight 顶层带 userId/month 会污染每日扫描

**现象**（2026-11-01 家庭模式设计评审时预判并挡住，未上线即避免）：
若家庭 insight 文档顶层带 `month`，会被 `listPendingInsightUsers` 的
`where({month})`（`shared/db/index.js:230`）每天捞进个人分析批次；
顶层带 `userId`（owner 的）还会与 owner 个人 insight 的 `generateTime` 混算，
家庭重算后 owner 个人结论**永不重算**。

**根因**：`users` 集合是混存集合 —— 个人 insight（`${openid}_insight`）、
用户档案（`${openid}_profile`）、家庭 insight（`family_${familyId}_insight`）
共处一集合，键空间靠 `_id` 前缀区分，但每日扫描按**字段**（`where({month})`）捞文档。

**修法**：家庭 insight 文档结构只有 `{ familyId, version, payload{month,...}, generateTime, updateTime }`
—— **顶层无 userId/month**；`saveFamilyInsight`（`shared/db/index.js:889`）自持字段白名单，
绝不复用 `saveInsight`（后者硬编码顶层 userId+month）。

**防线**：`cloudfunctions/shared/db/__tests__/family-store.test.js` 明确断言
「顶层不得有 userId / month」。家庭定时聚合（v2）接入时同样不能破坏这条隔离
（见 `business/04-family-mode.md` §5.1 / §10）。

## 62. `check-frontend` 跳过 `manage.*` 命名的页面

**现象**：新页面 `pages/xxx/manage.*` 的 WXML 绑定断裂**零报错**。

**根因**：`tools/check-frontend.js` 的 `resolvePageFiles` 只认同名文件或 `index.*`；
`manage.*` 命名解析不到页面文件 → **整页跳过** WXML 数据绑定校验。
`pages/category/manage`、`pages/recurring/manage` 现状即如此。

**修法**：新页面一律用 `index.*`（或与目录同名）—— 家庭模式页因此命名为
`pages/family/index.*`，享受完整绑定守卫。

**防线**：命名约定 + `npm run check:ui`。**命名不是小事** ——
「页面存在但守卫看不见」比「没有守卫」更危险。
