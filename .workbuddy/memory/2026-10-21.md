## analysis-svc timeout 调至 40s + 补 preflight 检查

用户要求改为 40s。顺带发现 preflight **只检查 bill-svc 的 timeout**，
analysis-svc 完全没纳入——这正是它之前配 15s 却没人发现的原因。

### 阈值算法（第一版写错了）

初版：`needSec = ceil(8000/1000) + 3 = 11`。
实测 15s 能通过——但 15s 实际不够，因为漏算了两件事：
1. `chatWithTools` 把总预算**分摊到每轮**（`max(800, 8000/3)` = 2667ms），
   单轮上限不是 8 秒
2. **冷启动 3~5 秒不计入 LLM 预算**，却实实在在吃函数总时长

修正后：`perRoundSec(3) + 数据处理(3) + 冷启动(5) = 11s`
三档实测：40s ✅ / 15s ✅ / 10s ✗ 正确判失败。

### 通用教训

**每个云函数的超时阈值要单独算，不能套用别人的。**
bill-svc 是单次 LLM，analysis-svc 是多轮往返 + DB + 冷启动，结构完全不同。
用同一个阈值去判，会把明显不够的配置判成「够用」——
而预检工具的职责恰恰是拦住这种配置。

另外：新增预检项必须**正反向验证**（改小配置看它是否真的报错）。
第一版就是只测了 40s 通过，没测小值，于是错误阈值活了下来。

## 分析读算分离：把 10 秒移出用户路径（版本 20261021-04）

用户要求「前端加分析按钮 + 后端定时分析 + 前端只读不触发」。
选择：**记账时自动触发**（而非定时器）+ **users 集合存储**。

### 核心决策：为什么不用定时触发器

定时是「按时间跑」，与用户何时记账无关：
- 月初集中记 30 笔 → 定时器只能等某个固定时刻
- 半年不记账 → 定时器仍在空跑、仍在烧 LLM 额度

挂在记账事件上才是**按需分析**：有多少真实数据就算多少。

### 三个状态必须区分（混在一起给错误引导）

`hasResult:false`（从没分析过→ 给按钮）
vs `hasResult:true + savings:[]`（分析了没空间 → 说明原因）
vs `isStale:true`（存的是上月→ 提示「本月尚未生成」）

**把上月结论当本月展示是错误信息，比显示「旧数据」严重得多。**

### 排查中发现的既有缺陷

**`opts.timeout` 从未被使用**：`wx.cloud.callFunction` 超时不可配置，
之前 `diag` 传 15000 是空承诺。已用 `Promise.race` 实现，
并区分「客户端主动放弃」（云端还在跑，提示不能是「升级套餐」）与「服务端 -504003」。
计时器必须在 finally 清理，否则累积上百个 pending timer。

**preflight 的集合提示写死「仅 bills 一个」**：
加users 后立刻变成错的，而它是用户建表的唯一依据。
已改为从 `REQUIRED_COLLECTIONS` 动态读取（并从 constants.js 取真实字符串值）。

### mock 的坑（这次又踩了一次同类）

内存版 users 集合只实现了 `doc().set()` 没实现 `doc().get()`，
读取时报「doc(...).get is not a function」，
而 `getInsight` 的 catch 把它吞成「文档不存在」——
现象是「明明写进去了却读不到」，根因却在 mock 上。

**mock 缺方法时，catch 会把 mock 的错伪装成业务状态**。这与之前
`recomputeSavingAmounts` 传错参数被 `Array.isArray` 静默降级是同一类问题。

## 改为定时任务：每天 0 点批量分析（版本 20261023-01）

用户改需求：「记账时不主动分析，改为每天晚上 12 点定时分析」。
移除了 bill-svc 里的 `triggerInsightRefresh`（4 处调用 + 函数 + import）。

### 关键查证：定时触发器没有用户上下文

官方文档明确：`getWXContext().SOURCE === 'wx_trigger'`，
且 **OPENID 为空**。所以定时任务不能问「给谁分析」，
必须自己从 bills 集合把待分析用户捞出来。

cron 是 **7 段**（秒 分 时 日 月 周 年），`0 0 0 * * * *` = 每天 0 点（UTC+8）。
**config.json 不能有注释**，否则触发器部署一直失败。

### 两个工程约束（决定了实现形态）

1. **40 秒只能跑约 3 个用户**（单个 10 秒）→ 按**实际耗时**判预算（32秒），
   不按固定数量；超预算的标deferred + 返回 nextCursor，下次续跑
2. **只算「账单有新增或结果过期」的用户**——判据是
   账单的 `createTime` 上限 > 结果的 `generateTime`，
   不需要额外字段也不用维护游标。否则每天给所有人重跑会烧额度。

### 防越权

`refreshInsight` 支持 `payload.targetOpenid` 供批量调度用，
但**只在 `SOURCE === 'wx_trigger'` 时接受**——
外部调用若能任意指定 openid，就等于可以给任意用户写数据。

### 排查时踩到的坑

用 `sed -i 'Nd'` 按行号删代码，**行号会随删除位移**，
导致后续删除打偏，把 `return {...}` 和 `catch` 一起删掉了。
`--check` 查不出「返回值缺字段」这类错误，
靠持久化测试（test-persist.js）才暴露出来。

**教训：删代码不要依赖行号**。要么用 Edit 精确匹配上下文，
要么删完立刻跑该模块的测试——本次就是靠测试拦住的。

## 排查「可以这样省」整块消失（版本 20261023-02）

用户截图反馈：分析页只有「消费习惯分析」，**「可以这样省」整块不见了**。

### 三个根因（都不是单一原因）

**1. 数值格式误判 —— 最隐蔽的一个**

`collectNumbersDeep` 收集工具返回的 `'500.00'`（字符串金额），
而 `findUncitedNumbers` 从正文「500 元」抽出 `'500'`。
字符串不等 → 判定「无出处数字」→ **模型路径几乎必然退回兜底**。

后果极严重：所有数值校验逻辑看起来都正常，
但界面永远显示「当前为规则版分析」，而用户可能根本没注意到。

修复：数字**按数值归一化**（`normalizeNumber`：500.00 → 500、38.10 → 38.1），
收集侧与校验侧都用同一把尺。

**教训：数值比较必须用数值，不能用字符串。**
「看起来相同」不等于「相同」——`'500.00' !== '500'`。

**2. 小样本门槛过严 → 建议被整块丢弃**

截图场景每类只有 1~2 笔，全卡在 `MIN_SAVING_BILLS=3`，
`hasSavings: false` → 前端 `wx:if="{{savings.length}}"` → 卡片消失。

**关键区分（之前没想清楚）**：
- 「按比例估算省多少」需要样本（1 笔推不出「这个类目能压缩 30%」）
- 「这一笔值不值得提」**不需要**样本——备注本身就是判断依据

所以单笔 + 有备注时，改按**该笔实际金额 × 20%** 给建议（更保守），
数字完全可追溯（就是那笔账的金额）。

**3. 空卡片让用户以为功能没做**

改成卡片始终显示，无建议时说明原因。
`buildSavingsEmpty` 区分「数据不足」与「全是刚性」两种文案。

### 我自己犯的设计错误：备注存在 ≠ 该省

第一版单笔建议选中了「95号油」和「同事聚餐」——
这两笔都有备注，但都是**该花的**：通勤不加油没法上班，请客不请没法做人。

新建 `util/essential-spend.js`：
- 必需性按**末级类目**判定（加油 vs 旅游度假必须区分，同一级不能一刀切）
- 社交支出（聚餐/请客/随礼/红包）也算必需——省它伤的是关系不是钱

**教训：数据完备 ≠ 判断正确。** 有备注只是有信息，
还得判断这个信息指向的是「可压缩」还是「不可省」。

### 验证

新增 `saving-rules.test.js`（13 项）覆盖三条规则。
全量 108 项全绿。模型路径实测跑通（isFallback: false）。

## 让降级原因可见（版本 20261023-03）

用户问「消费习惯分析目前还是规则版本？」——
暴露出一个诊断缺陷：**界面只显示「当前为规则版分析」，
但 `fallbackReason` 明明传到了后端，前端却不展示**。
用户看到一个现象却拿不到原因，只能猜。

### 关键设计：区分「故障」与「保护」

降级有 12 种触发码，性质完全不同：
- `NO_API_KEY` / `GLOBAL_LLM_DISABLED` → 用户配一下就好（config）
- `LLM_UNAVAILABLE` / `TOOL_LOOP_ERROR` → 临时故障，重试即可（retry）
- `NUMERIC_CITATION_MISMATCH` / `RIGID_CATEGORY_SUGGESTED`
  → **护栏正常工作**，不是故障（guard）

最后两类如果显示成「分析失败」，用户会以为系统坏了，
也会把「护栏在正常工作」误当成「功能没做」。

新建 `util/fallback-reason.js`，按 level 分三档，
前端按 level 用不同样式（guard 中性蓝灰、config 浅橙提示需动手）。

### 测试里最有价值的一条

「harness 里所有 finalizeWithFallback 的原因码都有对应文案」——
用正则从 index.js 抓出全部降级码，逐一断言有文案。
以后新增降级原因时若忘了加翻译，测试会立刻失败。

### 验证

有 Key 时消费习惯分析确实走模型路径（isFallback: false，
fallbackInfo: null），结论带判断，金额由代码重算（模型填 500 → 实际 100）。
全量 117 项全绿。

2. `preflight.js` 接入前端校验结果——
   它是「能不能真机调试」的最后一道闸，
   真机白屏的排查成本远高于跑一次脚本

### 验证（正反向）

注入同样的错误后：
- `check:ui` 报 `✗ miniprogram/pages/analysis/analysis.js 语法错误：
  SyntaxError: Unexpected identifier 'savingsEmptyText'`
  ——与真机报的**一模一样**
- `preflight` 报「前端校验发现 1 个问题」并列出具体行

### 教训

**「所有检查都通过」不等于「代码是对的」。**
当检查工具只做文本匹配时，它检查的是「文本是否符合预期」，
不是「代码是否能运行」。

**通用教训**：任何静态检查都应至少有一层是**真解析**，
否则漏掉的正是最致命的那类问题（语法错误 = 整页白屏）。

## Agent 执行链路可观测性（版本 20261023-04）

用户问「如何查看 agent 执行过程中调用哪些工具、出入参、模型输入输出」。

### 原状：什么都看不到

| 想看的 | 原状 |
|---|---|
| 调用了哪些工具 | ✅ 有（`tool_calls` 事件，但只有名字+成败） |
| 工具入参/出参 | ❌ 没有 |
| 模型输入 | ❌ 完全没有 |
| 模型输出 | ❌ 完全没有 |

而且 tracer 是**纯内存 buffer**，云函数实例一销毁就没了——真机上看不到任何东西。

### 实现

**1. tracer 增强**
- 按 traceId 聚合完整调用链（`chains` Map）
- `dumpChain()` 输出：结构化行（给工具解析）+ 人读版（带时间偏移）
- `safeStringify()` 防循环引用抛错——**埋点不能成为故障源**
- 详细模式默认关闭（账单金额是隐私），`DEBUG_TRACE=true` 才开

**2. llm-client 埋点**
- `callOnce` 记 `llm_request`（模型、参数、消息摘要）/ `llm_response`（输出、tool_calls、token、耗时）
- `chatWithTools` 记 `tool_call`（工具名、入参 args、出参摘要、耗时）
- **出参只记概要不记全文**：工具返回账单明细，全量进日志既刷屏又泄露隐私
- 按工具名定制摘要（`summarizeToolResult`），11 个工具各有重点字段

**3. tools/trace-view.js**
把日志还原成可读报告：模型输入 → 工具入参出参 → 模型输出 → 护栏判定。

### 关键设计：不要重复输出

最初 `logEvent` 逐条 console.log，`dumpChain` 又输出一次——同一件事两遍，
日志有长度上限，重复等于浪费预算，真正有用的信息反被截断。
改为：结构化事件只进内存链，结束时 dumpChain 统一输出一次。

另外 `rawMessages`（完整系统提示词 3000+ 字符）会淹没日志，
已移除——要全文看 agent 源文件即可。

### 使用方式

```
云函数控制台加环境变量 DEBUG_TRACE=true → 触发一次分析
复制日志 → node tools/trace-view.js trace.log
```

### 教训

**排查工具本身不能成为故障源。**
`safeStringify` 对循环引用返回占位符而非抛错——
否则「为了排查问题写的代码」会把正常流程搞挂。
