## 补充：DEBUG_TRACE 环境变量配在哪 + 补齐 trace 工具链的坑

用户问「DEBUG_TRACE=true 在哪里加」。

### 位置

**微信云开发控制台**，不在代码里：
云开发控制台 → 云函数 → analysis-svc → 「配置」标签页 → 环境变量 → 添加

键名 `DEBUG_TRACE`，值 `true`。只加 analysis-svc，bill-svc 不需要。

⚠️ **加完必须重新部署**：环境变量是实例启动时注入 `process.env` 的，
热实例读不到新值。重新部署会重启实例。

完整指引写在 `docs/how-to-trace-agent.md`。

### 顺手抓到的两个 bug

**1. `trace-view.js` 里 9 处 `p.payload` 用了未定义变量**
那些 `case` 分支里根本没有 `p`，只有 `s.payload`。
**只有走到「数值对账未通过」这类事件才会崩**——
而那恰恰是最需要看报告的时刻。

**2. `trace-demo.js` 的 mock 缺 `doc().set()`**
落库失败刷出一段无意义堆栈，干扰阅读（demo 的重点是 trace 不是落库）。

### 补的测试

`tools/__tests__/trace-view.test.js`（6 项），关键是：
- 构造覆盖**全部事件类型**的日志，逐个验证能渲染不崩
- 断言源码里不出现 `p.payload`（防止同类笔误复现）

「排查工具本身要可靠」——它出问题时你正依赖它。

### 文档里写错的命令

原先写「DEBUG_TRACE=true node tools/e2e-local.js」，
但 e2e-local.js **不调用 insight agent**，根本不会产生 trace。

## 架构调整：去掉数值对账，改为「工具依赖校验」（版本 20261024-01）

用户明确要求：「不需要做如此的对账，但如果需要获取相关数据，
请分析合理的入参要求后调用工具，没有合适工具，不做对应的分析结论」。

### 为什么换掉

原机制「模型写完 → 逐个数字查白名单 → 有对不上的整条作废」有三个问题：

1. **误伤率高** —— '500.00' vs 500 这种格式差异就判失败，
   实测导致模型路径几乎必然退回兜底
2. **粒度错** —— 一句话里其他正确的判断被一起推翻
3. **治标不治本** —— 它查「数字有没有出处」，
   查不出「这个结论本来就没有工具能支撑」

### 新机制

```
维度 → 所需工具的映射表（CONCLUSION_REQUIRES）
     ↓
模型调了哪些工具（collectToolUsage）
     ↓
结论涉及的维度里，有没有工具被调用过
     ↓
没有 → 那条结论剔除（不是整条作废）
```

**关键：粒度从「整条」改成「单条结论」。**
用户看到少一句有根据的话，比什么都看不到要好。

### 复合结论的判定：任一维度有支撑即成立

第一版写成「所有维度都要有工具」→ 误杀严重。

实测：「刚性支出 200 元，占 13.8%（孩子学费）」
—— 主体是刚性（查过），顺带提了占比（没查），结果整条被剔。

改成**任一维度有支撑即保留**。理由：一句结论常常是复合的，
主体站得住就够。数值安全由「金额兜底重算」兜住
（模型填的金额一律作废），这里只管「有没有查过」。

修完：同样场景从「结论 0 条」变成「结论 3 条」。

### 工具入参：报错而非静默夹住

原来 `clampInt(args.n, 1, 5, 3)` —— 传 999 夹到 5，传 'abc' 当默认。
模型不知道自己传错了，会基于**错误理解的数据**下结论。

改为：`validateArgs` + `TOOL_ARG_SCHEMAS`，非法入参直接报错回传，
让模型能自我纠正（工具报错必须回传，这是模型唯一的修复途径）。

同时给工具补了入参：
- get_category_share / get_noted_bills / get_savings_potential → category
- get_top_categories → n（已有）
- get_trend → monthCount（已有）

### 刚性检查也改成剔除粒度

原来一条建议违规就整条退回。现在只剔除违规项，保留其余。
且顺序调整为：**工具依赖 → 刚性 → 金额重算**——
已被剔除的建议不该再报刚性违规。

### 顺带发现

`guardrail.validateNumericCitations` 是死代码——
`options.authoritativeValues` 全项目无人传入。已删。

### 测试

新增 `tool-grounding.test.js`（11 项），覆盖：
各维度有/无工具的保留与剔除、复合结论不误杀、
完全没调工具才退回、非法入参报错、数字格式差异不再导致降级。

全量 145 项全绿。

## 为什么还是规则版分析？（版本 20261024-02）

用户反馈改完架构后仍显示规则版。

### 根因：分析页读的是「已存的旧结果」，不是现算

`loadInsight()` → `readInsight()` → `db.getInsight()`，**完全不触发计算**。
只有「立即分析」按钮（`refreshInsight`）和定时任务才会跑 LLM。

所以用户看到的「规则版分析」是**之前那次分析存下来的旧数据**——
改代码不会改变它，必须重新触发一次分析。

这与「分析要10秒，不能让用户等」的读算分离设计是一致的，
但代价是：**改代码后必须手动重算才能看到效果**。

### 顺带发现：无法自查是更根本的问题

「显示规则版」有 5 种可能原因（代码没部署 / Key 没配 / 读到旧结果 /
LLM 被关 / 模型调用失败），靠猜要浪费大量时间。

之前 `analysis-svc` **没有 diag 入口**（只有 bill-svc 有），
所以用户连「到底卡在哪一环」都看不到。

### 新增：analysis-svc diag（一次给出答案）

`action: 'diag'`，检查 7 项：
SDK、用户身份、数据库、LLM 开关、API Key、**已存结果的状态**、**模型实测**。

**关键：模型实测是真的发一次最小请求**，
而不是只读 `process.env`——因为环境变量可能配了但没生效
（热实例没重启、配到了别的函数）。实测才说明问题。

输出还带 `advice`（可执行的下一步）和 `codeVersion`（判断云端代码是否已部署）。

前端在分析页加了「为什么是规则版？点这里诊断」按钮，
降级时才出现，诊断结果面板里版本不一致会单独高亮。

### 教训

**改完代码要能让人立刻看到效果。**
读算分离的设计下，「打开页面看到旧数据」是正常行为，
但必须提供「重算」入口 + 「为什么没生效」的诊断，
否则用户只能反复问「怎么还没变」。

## 🔴 根因：云端从来没有全局 fetch（版本 20261024-03）

用户跑完诊断（新增的 analysis-svc diag）得到：
```
{"name": "模型实测", "ok": false, "detail": "模型调用失败：fetch is not defined"}
```

**这不是诊断的问题——它暴露了 LLM 路径在云端从未成功过一次。**

### 事实

微信云函数运行时 `Nodejs18.15` + CommonJS 上下文下，**全局 fetch 不存在**。

原因：Node 18 的 fetch 是实验特性，**只在 ESM 上下文注入 globalThis**。
本项目全部用 `require`（CommonJS），所以拿不到。

**最坑的地方**：本地 Node 22 有全局 fetch，
所以**本地测试全绿、云端必然失败**。这就是「本地全绿 ≠ 云端能跑」的又一例。

社区里踩同样坑的人给的解法一致：**云函数里别用 fetch，用 https 模块**。

### 修复

新建 `shared/util/http-client.js`：基于 Node 内置 `https` 模块实现 POST，
零依赖零安装。接口刻意做成 fetch 风格（ok/status/text()/json()），
调用处几乎不用改。

`llm-client.js` 改为 `httpClient.postJson(...)`。

**顺带一个隐蔽 bug**：删掉 AbortController 时，`finally { clearTimeout(timer) }`
引用了已删除的 `timer` 变量 → **每次请求都抛 ReferenceError**。
这类错误 `node --check` 查不出来（语法合法，运行时才炸）。

### 测试必须 mock 同一个东西

原来 3 个测试文件都 mock `global.fetch` —— 那测的是**本地 Node 22 的假路径**。
改为注入 http-client 的 `__setImpl()`。

新增 `tools/__tests__/http-mock.js` 统一提供 mock。

**教训：mock 的东西必须与生产走同一条路。**
否则测试全绿只证明了「本地那条路能通」。

### 验证

模拟云端环境（`delete global.fetch`）实测：
```
typeof fetch = undefined
✓ 请求已发出，model= deepseek-chat messages= 1
调用结果 ok= true
✅ 无 fetch 环境下 LLM 调用正常
```

### preflight 新增 [8/9] 云端运行时能力

- 扫业务代码里的**残留 fetch 调用**（排除 __tests__），报文件:行号
- 确认 http-client 可加载、https 模块可用
- 提示本地与云端的差异

反向验证：注入一处 fetch 后能准确报出 `http-client.js:164`。

### 教训

**「本地能跑」不等于「云端能跑」，差距往往在运行时能力上。**
Node 版本、模块系统（ESM/CJS）、全局 API 可用性——
这些差异本地测不出来，必须显式模拟云端环境测一遍。

## 修复：「近半年趋势图没有画出来」（WXML ↔ 数据契约断裂）

用户报：近半年趋势图没有画出来。

### 根因：字段契约断裂，全程零报错

`analysis.wxml` 的趋势循环绑了：
```xml
<view class="trend-bar" style="height:{{item.height}}%"></view>
<text class="trend-month">{{item.label}}</text>
```

但云函数 `billStats.calcTrend()` 只返回：
```js
{ month, totalCent, totalYuan, count }
```

**没有 `height`，也没有 `label`。**

于是：
- `height:{{item.height}}%` → `height:undefined%` → **非法 CSS 被浏览器直接丢弃**
  → 柱子只剩 wxss 里的 `min-height: 4rpx` → 看起来就是「图没画出来」
- `{{item.label}}` → 空 → 月份标签也全没了

**最难查的地方在于零错误信号**：云函数返回正常、`month`/`totalYuan` 都在、
只有两个「画图专用」的字段缺失。界面上只是「图不见了」，没有任何报错。

### 为什么在前端修而不是云端

1. **存量数据立刻生效**：分析结果已落库在 users 集合，存的是旧结构。
   云端补字段要等下一次分析（凌晨 0 点定时任务）才生效；
   前端补则立刻对存量数据生效，**不必重算、不必部署云函数**。
2. **柱子多高是展示层的事**，云端不知道画布多高。
3. **`get_trend` 工具的输出直接进模型视野**——
   塞 height/label 会污染模型读数（模型可能把 "66.7" 当成消费额，数字对账立刻失效）。
   这条与「tools 化改造」的核心原则一致：模型视野里只放它需要的语义数据。

### 改动

**新增 `miniprogram/utils/trend.js`**（视图模型）
- `buildTrendView(rawTrend)` → `[{ month, label, totalYuan, count, height }]`
- 柱高 = 该月 / **当月最高值** × 100
- 高度用**整数分**算，不碰 totalYuan 字符串（避免浮点误差）
- **零消费月份高度必须是数字 0**（不是 "0"、不是 "0%"）——
  wxss 的 `.trend-bar[style*="height:0%"]` 靠精确匹配画灰色基线
- 有消费但金额极小的月份给 `MIN_VISIBLE_PERCENT = 2` 的下限，
  否则四舍五入成 0 → 视觉上等同「这个月没花钱」，比柱子矮更误导
- 标签「10月」；跨年窗口首列带年份（「25年12月」），避免「1月」是哪年看不出来

**`miniprogram/pages/analysis/analysis.js`**
两处 `trend: d.trend || []` → `trend: buildTrendView(d.trend)`
（loadInsight 读已存结果、onRefresh 手动重算，两条路径都要走）

### 两条防线

**1. 契约测试 `tools/__tests__/trend-view.test.js`（14 项）**

关键的一条是**从 analysis.wxml 真解析**出趋势循环绑了哪些字段，
再断言视图模型必须全部产出：

```js
const missing = [...bound].filter((f) => !(f in item));
const undef = [...bound].filter((f) => item[f] === undefined);
```

⚠️ **只查 key 存在是不够的**——「有 key 但值是 undefined」正是原始 bug！
第一版契约测试只查 key，注入 bug 后它**照样通过**；
加上值断言后立刻抓到：
```
这些字段的值是 undefined（WXML 绑定看着正常，运行时却拿不到值）：height, label
```

这验证了 MEMORY 里那条教训：
**「所有检查都通过」不等于「代码是对的」**——
只有真解析 WXML 并与数据契约对账，才能发现这类静默断裂。

**2. `check-frontend.js` 新增 WXML 数据绑定守卫**

原来只查事件处理器（bindtap）与 require 导出，**完全不看数据绑定**。
现在对每个 wx:for 循环，解析出 `{{item.字段}}`，检查该字段名
**在整个数据链路上**都出现过。

⚠️ **搜索范围必须是整条链路，不能只看页面 JS**：
第一版只搜页面 JS，误报了 savings 的
title/amount/action/trigger/reason——那些是**云函数**产出的，
页面只是透传 `d.savings`。现在范围 = 小程序全部 JS + 云函数全部 JS。

### 顺手修的两个既有 bug

**A. `check-frontend.js` 只检查 index 页**
硬编码 `index.${ext}` → analysis / detail / profile 三个页面的
WXML 事件绑定、require 导出**从来没被校验过**。

现在按目录里的实际文件名解析（`resolvePageFiles()`）。

**B. 两处 `const` 暂时性死区（TDZ）**
`const` 在声明之前引用会抛 ReferenceError，不是 undefined：
- `cloudfunctions/shared/agent-harness/tools/__tests__/tool-grounding.test.js`
  mockHttp 第 83 行 require、第 48 行调用
- `tools/trace-demo.js` httpClient 同理

两者都让 `npm test` **中途崩溃**，后面的测试根本没跑——
**包括我新加的趋势测试**。修复：把 require 提到使用点上方。

### 教训

**WXML 绑一个数据源没有的字段，运行时是「静默塌陷」而不是报错。**
CSS 里 `height:undefined%` 这类非法值被静默丢弃，
界面上表现为「某个模块不见了」，日志里什么都没有。

数据契约要像接口一样有测试兜底：
- 精确到字段级 → 契约测试（真解析 WXML + 断言值不是 undefined）
- 广撒网 → 静态检查守卫（字段名在整个数据链路上出现过）

**另外：改完测试要确认 `npm test` 能跑完整条链**，
不能只看最后一个文件的输出——中途崩溃会让后面的测试静默不跑。
