## 放弃微信插件，改用腾讯云流式 ASR（版本 20261018-05）

**放弃原因（两条都是硬约束）**：
1. **微信同声传译插件仅对非个人主体开放**。个人主体小程序在「设置→第三方设置→插件管理」里
   搜不到该插件，服务端返回 `permission deny` 错误码 **80082**，预览直接失败且不提示去申请。
   （多个独立信源确认：微信开放社区智能回答、腾讯位置服务/腾讯云直播接入文档、掘金/CSDN 实操文）
2. **不支持流式上屏**。官方 recordRecoManager 只有 onStart/onStop/onError 三个回调。

**实现**：
- 新增 `cloudfunctions/asr-svc/asr-client.js`：手写 WebSocket + HMAC-SHA1 签名，
  **不引入 tencentcloud-sdk-nodejs**（那是全产品 SDK 很大；流式识别只需签名+WS）。
  关键实现点（全部核对自官方文档 cloud.tencent.com/document/product/1093/35800）：
  · 签名：参数按字典序排序 → 拼 `asr.cloud.tencent.com/asr/v2/{appid}?{qs}` → HMAC-SHA1 → base64 → **必须 urlencode**（漏掉会偶发 4002）
  · **1:1 实时率分片发送**：16k/16bit/单声道下每 200ms 发 6400 字节。一次性全发必被服务端断开
  · 空超过 15s 报 4008 → 加 8s 保活空包
  · slice_type 1=非稳态（可上屏）2=稳态（确定），final=1 表示流结束
  · **签名算法已用官方文档示例参数实测验证通过**
- 重写 `cloudfunctions/asr-svc/index.js`：`recognize`（真实实现）/ `cleanup` / `status`（自检）。
  未配凭证时返回 `ASR_NOT_CONFIGURED` + `fallbackable:true` 供前端降级。
- 重写 `miniprogram/utils/voice.js`：删除全部插件逻辑，只保留 CLOUD + MANUAL 两级；
  `explainAsrError()` 把腾讯云错误码（4002鉴权/4003未开通/4004额度耗尽/4005欠费/4006并发超限…）翻译成人话。
- `app.json` 移除 plugins 段；`app.js` 移除 `__pluginMap`。
- preflight 语音段整体重写：校验实现完整性、签名含 HMAC+urlencode、分片实时率、
  **硬编码密钥检测**（安全事故守卫）、app.json 插件残留、录音参数与 16k_zh 引擎匹配。

**已知限制（已在代码注释说明）**：云函数是一次性调用，无法把流式中间结果实时推回前端，

### 修「真机录音阶段失败」（版本 20261018-07）

现象：云函数 status 测试正常，但小程序真机上**录音阶段就失败**（非识别阶段）。

**先排除一个错误假设**：我一度怀疑是 `app.json` 缺 `requiredPrivateInfos`。
查官方文档确认 `requiredPrivateInfos` **只接受地理位置那 8 个接口**
（getFuzzyLocation/getLocation/onLocationChange/startLocationUpdate/
startLocationUpdateBackground/chooseLocation/choosePoi/chooseAddress），
**与录音无关**。项目里 preflight 的判断是对的，无需修改。搜索结果里说
「录音要写 requiredPrivateInfos: ["record"]」的说法是错的博客内容。

**实际的改进（让报错可见，而不是让用户瞎猜）**：
- `ensurePermission()` 原来 `catch { return false }` —— 不管用户拒绝、弹窗失败还是
  getSetting 异常，一律返回 false 并统一提示「未获得录音权限」。
  真机上真实原因可能是「曾拒绝过需引导设置页」「开发者工具勾了不校验域名但真机没开」
  「iOS 时序竞争」「AppID 权限不足」，全被压成同一句话。
  改为返回 `{ granted, reason }`，把真实原因带到 UI。
- 新增 `explainRecorderError()`：把 wx.getRecorderManager 的英文 errMsg 翻译成可执行动作
  （auth/deny → 提示去设置页开权限；not start/busy → 重进小程序；simulator → 提示用真机）。
- `start()` 把 `this.init()` 提到权限申请之前：authorize 弹窗期间用户可能松手，
  监听注册太晚会漏掉 onStop/onError，表现为「按了没反应」。
- 清理 `index.js` 里的 `onChannelFallback` 死代码（插件方案遗留，已无对应实现）。

**待用户提供信息才能定位**：真机的具体报错文案。若改动后仍失败，
优先排查真机调试是否开启「不校验合法域名」（`uploadFile` 到云存储会被拦）。

### 定位到真因：录音器状态机缺保护（版本 20261018-08）

报错原文：`operateRecorder:fail is recording or paused`
—— 意思是**录音器还处于录音/暂停态**，是上一轮失败留下的残留状态。

**根因（两个，都在我上一轮的改动范围内）**：
1. `onRecordCancel()` 只调 `reset()`，而 `reset()` 只改本地 state、**不碰真正的录音器**。
   用户划走取消时录音器仍在录 → 下次按下必报这个错。
2. `start()` 是 async（`await ensurePermission()` 要等权限弹窗），
   这期间用户松手时 `stop()` 会因 `state !== RECORDING` 直接 return，
   录音器就永远开着。另外快速连按也会并发调两次 `start()`。

**修复**：
- `voice.js` 新增 `starting` / `cancelRequested` 两个标记：
  · `start()` 用 `starting` 防并发；await 权限后检查 `cancelRequested`，被取消则不下发 start
  · `stop()` 在 `starting` 期间改为记取消意图（而非直接 return）；否则无条件下发 `_stopRecorderQuietly()`
  · 新增 `abort()`：强制中止（reset + 无条件停录音器），供取消/卸载用
  · `reset()` / `destroy()` 清这两个标记
- `index.js`：`onRecordCancel` 改用 `voice.abort()`；`onUnload` 先 `abort()` 再 `destroy()`
- preflight 新增 4 项守卫：starting/cancelRequested 保护、abort() 存在、
  onRecordCancel 用 abort、onUnload 先 abort 再 destroy

**教训**：`wx.getRecorderManager` 是**全局单例**，其真实状态与本地 state 可能不一致。
不能靠本地状态变量推断录音器状态，stop/abort 必须能无条件下发。
这类「UI 状态 vs 系统资源状态不同步」的问题在录音/相机/定位上都会踩。

### 修「语音识别失败，请手动输入」（信息被吞，版本 20261018-09）

现象：录音通了，但识别失败，前端只显示兜底文案，看不出真实原因。

**根因：`utils/cloud.js` 包装层把 `result.message` 丢了**。
云函数失败时返回 `{ ok, error, message, hint }`，但封装层只拼了 `error + hint`。
而 `message` 往往才是定位问题的关键（含腾讯云原始报错）→ 前端只剩一句「执行失败」。

修复：
- `utils/cloud.js`：`result.ok === false` 时把 `error` / `message` / `hint` **全部**拼进Error，
  并挂结构化字段 `err.errorCode` / `err.hint` / `err.raw`，调用方可直接判断而不必正则匹配文案。
- `voice.js` `explainAsrError()` 重写：① 用 `err.errorCode` 判断（不再靠正则猜）；
  ② 腾讯云错误码表从 9 条补到 17 条（4000~6001 全覆盖）；
  ③ **兜底时保留原始报错**（截断 120 字），不再把真实原因藏起来。
- `asr-svc/index.js`：catch 分支改为返回 `{ error: e.errorCode||'ASR_INTERNAL_ERROR', message: 'xxx 失败：...' }`。
- `asr-client.js`：新增 `resolveWebSocket()` 实际探测 WebSocket 可用性
  （本地 Node 22 有不代表云函数 Node18.15 有——又是一个「本地能跑云端 undefined」的坑），
  并在连接前打日志 `[asr] 运行时 vX，WebSocket: available`。
  失败时给出明确指引（改 config.json 的 runtime）。
- `asr-svc` `status` action 新增 `webSocket` / `runtime` 字段，与凭证缺失**分开报告**
  （两个独立故障，混在一起没法排查）。已实测：webSocket 可用 + runtime v22.22.2。

**方法论**：封装层包装错误信息时，要把后端返回的**所有**诊断字段透传，
而不是只挑一两个自己看得懂的。否则「前端兜底文案」会永远吞掉真正的错误。

### 加 selfTest：把「部署/运行时/凭证/腾讯云」四类问题一次分开（版本 20261018-10）

第二次出现「语音识别失败，请手动输入」，说明 message 里仍无可匹配内容——
问题在 status 覆盖不到的环节（音频下载 / WebSocket 握手 / 腾讯云鉴权 / 协议交互）。

新增 `asr-svc` 的 `selfTest` action：用**环境变量里的真实凭证**真正发起一次
WebSocket 握手（只握手不发音频），一次调用即可区分：
- 握手成功 → 部署/运行时/签名/凭证全正常，问题在音频上传或前端调用
- 4002 → 签名或密钥错误
- 4003 → 腾讯云服务未开通
- 4004 → 额度耗尽
- HANDSHAKE_TIMEOUT / WS_ERROR → 网络或运行时

同时给 `voice.js` 的「未返回文本」路径加结构化错误码 `ASR_EMPTY_RESPONSE`
（原来是裸字符串，必然落到兜底文案），并补 `ASR_INTERNAL_ERROR` 分支；
catch 里改为 `console.error` 打印 `{message, errorCode, raw}` 三个字段，
真机日志能直接看到云函数返回了什么。

**排查方法论**：当「A 检查正常但 B 失败」时，不要继续猜 B 的原因，
而是加一个**能区分故障层级的探测入口**。status 只验证了「凭证存在 + 有 WebSocket」，
不验证「能不能连上腾讯云」——中间隔了签名、网络、鉴权三道关。

### 真因：cloudPath（相对路径）被当成 fileID 传给 downloadFile（版本 20261018-11）

报错 `downloadFile:fail 503003`。查官方错误码表：**-503003 = 云存储文件不存在**
（另有「签名无效」同码，是官方文档已知冲突）。

**根因**：`voice.js` 里 `cloudPath` 是 `asr/xxx.mp3` 这种**相对路径**，
我直接把它当作 `fileID` 传给了云函数，而 `sdk.downloadFile({ fileID })`
只接受 `wx.cloud.uploadFile()` 返回的**完整 `cloud://` URL**。

**这个 bug 极隐蔽**：上传明明成功了（返回了 fileID 但我没接），
是下载侧找不到文件。表现为「录音成功 → 识别失败」，极易往 ASR 方向排查。

修复：
- `voice.js`：接住 `uploadFile` 返回的 `fileID` 并传云函数；cloudPath 仅作日志/兜底；
  上传失败时把 `message/errMsg` 带上（原来统一说「上传录音失败」）；cleanup 也传 fileID。
- `asr-client.js`：下载前**显式校验** `fileID` 必须 `cloud://` 开头，否则抛出明确说明；
  对 `-503003` 单独诊断（列出三种可能原因：fileID 格式错/ 已被清理 / 云函数与小程序不同环境）；
  加 `[asr] 下载录音:` 与 `[asr] 音频大小 N字节` 日志。
- `asr-svc/index.js`：`recognize({fileID, cloudPath})`；缺 fileID 返回 `ASR_BAD_ARGUMENT`；
  `cleanup({fileID, cloudPath})` 优先用 fileID。
- preflight 新增 3 项：前端传完整 fileID、云函数校验 fileID 格式、对 -503003 有专门诊断。

**同时修掉检查器自身的误报**：新加的 fileID 检查用了 `/^\(cloud/` 这种正则，
在多层字符串里转义出错，把正确的代码判成 ✗。改用 `String.includes` 判断——
正则转义在 preflight 这种「检查代码的代码」里本身就是风险。

**教训（跨领域通用）**：云存储 API 区分「路径」与「标识符」两种概念。
uploadFile 接受相对路径，downloadFile / deleteFile 只认完整 fileID。
**上传成功 ≠ 下载能拿到**——中间隔着标识符形态转换。

### 真因二：云函数运行时没有内置 WebSocket（版本 20261018-12）

报错 `当前云函数运行时没有 WebSocket 实现`。

**这次是我判断失误**：我在本地用 `node -e` 测到 `globalThis.WebSocket` 是 function，
就断定云函数 Nodejs18.15 也有。实际上：
- Node 22 内置 undici，globalThis.WebSocket 默认可用
- Node 18/20 的 WebSocket 是实验特性，需 `--experimental-websocket`
- **微信云函数是精简构建，指望不上内置实现**

本地探测无法代表云端——这是本项目「本地全绿≠云端能跑」系列里最隐蔽的一次，
因为**探测代码本身**就写错了。

**修复**：
- `asr-svc/package.json` 加 `"ws": "^8.18.0"`（必须「上传并部署：云端安装依赖」才会装上）
- `asr-client.js`：
  · `resolveWebSocket()` 改为 **ws 包优先**，全局仅作兜底
  · 新增 `openSocket(url, handlers)` **统一封装**：屏蔽 ws 包（EventEmitter 风格 `on()`）
    与浏览器风格（`onmessage` 属性）的差异，上层只写一套代码。
    **直接写 `ws.onmessage = fn` 在 ws 包上不会触发**——这是换成ws 包后最容易踩的新坑。
  · 主流程与 selfTest 全部改用 openSocket，避免两处实现分歧
- `status` 增加 `globalWebSocket` 字段，明确区分「本地有全局」与「云端靠 ws 包」；
  `selfTest` 的 NO_WEBSOCKET 提示改为「确认 package.json 声明 ws 并用云端安装依赖部署」
- preflight 新增 2 项：`asr-svc/package.json` 必须声明 ws、必须用 openSocket 统一封装

验证：删除 `globalThis.WebSocket` 模拟云函数环境，实测 `resolveWebSocket()` 仍返回
ws 的 WebSocket 构造器，事件适配正确触发 err/close。全绿无✗。

**教训**：验证「运行时是否支持某能力」时，**探测语句必须在目标环境成立**。
本地测出true 就写进代码，等于把假设固化。

### 真因三：小程序调用云函数有 3 秒网关上限（版本 20261018-13）

真机报错 `-504003FUNCTIONS_TIME_LIMIT_EXCEEDED, Invoking task timed out after 3 seconds`。
**此时 ASR 已跑通**（截图里识别出「买菜1万块。」），是后续记账环节超时。

**根因（架构级疏漏）**：我一直假设客户端能一直等云函数。实际上
**小程序调用云函数有3 秒网关上限**，而腾讯云流式识别要求 1:1 实时率发送音频——
10 秒录音就要传 10 秒，同步等待必然超时。

**修复：改为「异步 + 轮询」（微信官方标准做法）**：
- `asr-svc` 新增 `startRecognize`：立即返回 `jobId`，识别在后台跑，
  结果写入模块级 `JOBS` Map；**必须设 `context.callbackWaitsForEmpty = false`**，
  否则云函数会等后台任务结束才返回，3 秒上限照样触发。
- 新增 `pollResult`：返回 running / done / error 三态；
  **job 查不到时返回 `JOB_EXPIRED` + retryable=true**——
  云函数实例可能被回收，前端必须能终止而非无限轮询卡死。
- `voice.js`：新增 `_pollJob()`，间隔 1200ms，
  超时预算 = `estimateMs × 2.5 + 5s`（上限 90s）——
  **不写死**：写死 60s 会误杀长录音，写死 10s 会让长录音白失败。
- **录音清理从 `finally` 移到失败分支**且只在 `!startedJobId` 时执行：
  识别成功后由云函数自己删（识别完即删）；提前删会让后台 `downloadFile` 报文件不存在。
- preflight 新增 4 项：异步 action 存在、前端用轮询、callbackWaitsForEmpty=false、cleanup 不在 finally。

**实测验证**（本地跑通 5 个路径）：
缺 fileID→ASR_BAD_ARGUMENT / 启动→立即返回 jobId / 立即轮询→running /
失败后轮询→透传真实错误 / 查无此 job→JOB_EXPIRED+retryable。

**再次修掉检查器假阳性**：新加的 `/finally[\s\S]{0,200}action:'cleanup'/`
误判——因为**注释里提到 "finally" 这个词**也被匹配到。改用
`/finally\s*\{[^}]*action:\s*'cleanup'/`（要求 finally 后紧跟 cleanup）。
这是本项目第三次犯「检查器的正则本身有 bug」——**检查代码的代码不该有假阳性**。

## 重要纠错：「小程序调云函数有 3 秒上限」是错误说法（版本 20261018-14）

真机又报 `-504003 Invoking task timed out after 3 seconds`（status_code 433），
用户问「为啥 3 秒？是哪个步骤？」——**这个问题问得好，戳破了我一直沿用的错误认知**。

查证腾讯云官方文档（docs.cloudbase.net）结论：
- **3 秒是云函数 timeout 的默认值，不是平台硬限制**
- timeout **可调至 1~900 秒**（普通函数），调高后客户端会等函数执行完
- 报错里的 "3 seconds" 指的就是**用户云函数自身的 timeout 配置**
- **已知坑：云函数配置只对 $LATEST 生效**，
  若调用落到已发布版本，timeout 修改不生效 → 这正是「config.json 写了25 实际跑 3 秒」的原因
- 官方 FAQ 给的长耗时方案：调大 timeout + 函数内 callback() 提前返回 + 结果写库/客户端轮询

按用户选择（方案 A：先保可用）：
- `LLM_TIMEOUT_MS` 5000 → **2200**，`LLM_RETRY_LIMIT` 2 → **0**
  （在 timeout 问题定位前，代码侧假设只有 3 秒可用；超时即走规则降级）
- constants.js 注释**明确写下这个纠错**，避免错误说法继续传播
- preflight 新增守卫：读 config.json 的 timeout +
  从 constants.js 实际读 LLM_TIMEOUT_MS 做比对（不写死数字），
  timeout 够大时提示「可放宽 LLM 预算以提升准确率」

**元教训（本日第 4 次同类问题）**：我又把「博客/经验说法」当成了事实，
还写进了代码注释并当成设计依据。查证只需一次 WebFetch，
成本远低于让错误认知污染整个方案。**凡是要写进注释当依据的外部结论，先查官方文档。**
