## 语音记账的备注总结（LLM）

需求：用户语音输入账单时，用大模型总结描述内容生成备注；大模型生成失败时，
把用户语音输入内容**全部**设置为备注。

### 实现

**新增 `shared/util/note-summary.js`** —— 备注合成的唯一入口：
```
buildNote({asrText, llmNote}) → 备注
  ① LLM 总结可用且没丢关键词 → 用总结（≤30 字）
  ② LLM 总结可用但丢了关键词 → 原话全文（≤200 字）
  ③ LLM 不可用 / 没给摘要   → 原话全文（≤200 字）
```
- `cleanLlmNote`：去引号、剥金额（「无」「暂无」视为没给）
- `lostKeywords`：比对原话与总结的关键词差集
- 长度：`MAX_NOTE_LENGTH=30`（总结）、`MAX_FALLBACK_LENGTH=200`（原文兜底）

**新增 `shared/util/note-keywords.js`** —— 关键词单一数据源。
原先 `RIGID_KEYWORDS` 硬编码在 `category-compressibility.isRigidBill` 内、
`ESSENTIAL_NOTE_WORDS`/`SOCIAL_NOTE_WORDS` 硬编码在 `essential-spend.isEssentialSpend` 内。
备注改成 LLM 总结后，这两个判定**完全依赖备注原文**，关键词散落三处必然漂移
（改了一处另一处没改 → 刚性保护静默失效）。
现三处统一从 `note-keywords.js` 取，并新增 `SCENE_LABELS`（规则层 scene 是英文代码
friends/unit，转中文短语给用户看）。

**改 `bill-parse.agent.js`**
- schema 加 `note` 字段（**刻意不进 required**：LLM_RETRY_LIMIT=0 时一次校验失败
  就是永久降级，少个备注不该让整笔账退回规则兜底）
- Prompt 新增「### 备注」段：15 字以内、保留人物关系与事由、**绝不写金额/日期**、绝不编造
- 输出示例加 note 字段
- fallback 路径：`note: ''`（不在 agent 层做规则提炼，由 bill-svc 统一合成）
- fallback 的 `scene` 从 `ruleParsed.scenes.join(',')`（英文代码）改为中文短语

**改 `bill-svc/index.js`**
- `mergeParseResult` 增加 `note` 字段，签名加 `asrText` 参数
- 落库 `note: finalData.scene` → `note: finalData.note`（**这是本需求的正题**：
  原来写的是 scene，兜底路径下是英文代码，用户在明细页看到的是「friends」）
- `prefill.note` 回传前端
- `buildBill` 的 note 统一裁到 200 字（与 amend 校验上限一致，
  否则一条超长备注在明细页编辑时会被 maxlength 截断，存回去就变了）

- `onOpenCategoryPicker` 的 `manualNote` 预填总结结果
- WXML：已入账卡片加 `.saved-note` 胶囊，确认/引导卡片加 `.confirm-note` 行

### 两个关键设计决策

**① 关键词丢失 → 退回原文，而不是拼接**
模型把「孩子学费3200」总结成「教育支出」，刚性判定立刻失效 →
分析页建议「学费可以省 30%」。这是本项目最贵的事故类型
（见 MEMORY「刚性支出：建议的禁区」）。
拼接方案（「教育支出·学费」）读起来像机器拼的故障，原文本来就是用户自己说的话，
最自然也最完整。所以检测到丢词就整体退回原文。

**② 兜底路径的备注里带金额 —— 这是有意的**
需求明确要求「模型失败时把用户语音输入内容全部设置为备注」。
与「备注不含金额」原则冲突，但取舍清楚：兜底意味着「模型没帮上忙」，
此时信息完整优先于格式规整。且明细页金额是独立字段（bill.amount），
不参与任何计算，不会对账出错。已在 `note-summary.js` 注释里写明这个取舍。

## 双盲对照实验：Wiki 到底能不能支撑变更？（重要结论）

### 实验设计
5 个真实变更需求，两组 agent 并行作答，互不可见：
- **A 组（Wiki 组）**：只准读 `docs/wiki/`，禁止读源码
- **B 组（源码组）**：只准读 `cloudfunctions/`/`miniprogram/`/`tools/`，禁止读 `docs/wiki/` 与 PRD

判据不是「谁写得好」，而是**已验证的事实**（grep / node 实跑）。

### 结论一句话
> **Wiki 提供「判断」，源码提供「坐标」。缺任何一半都做不成事。**

| 能力 | 只读 Wiki | 只读源码 |
|---|---|---|
| 架构判断（该怎么做/有什么坑/要不要找产品） | ✅ 5/5 全对 | ⚠️ 会跑偏 |
| 口径纪律（数值铁律/读算分离/单一数据源） | ✅ | ⚠️ 需重新推导 |
| 与 PRD 非目标冲突 | ✅ **只有 A 组发现** | ❌ |
| 定位坐标（常量在第几行/action 名） | ❌ 大量推断错误 | ✅ 精确 |
| 发现既有代码与需求冲突 | ❌ **完全漏掉** | ✅ 全找到 |
| 发现隐含算法缺陷 | ❌ 漏 | ✅ 全找到 |

### 三个实测反例（都亲自复核过）
1. **金额上限散在 4 处、3 种单位** —— Wiki 组只推出 1 处：
   `constants.js:100`(元) / `money.js:100`(分,硬编码) / `bill-svc/index.js:71`(分,硬编码) /
   `bill-parse.schema.js:20`(元，`maximum:500000` 比 50000 元宽松 10 倍，**从没生效过**)
2. **改「编辑面板字段」会撞上两条反向断言** —— Wiki 组完全没提：
   `tools/__tests__/edit-bill.test.js:93` + `tools/check-frontend.js:474`
   （都断言「编辑面板不含支付方式」→ 需求推翻旧决策时不改这两处，CI 全红）
3. **「12万」根本解析不出来** —— `cnToNumber` 单位表只到「千」，
   实测 `12万`/`二十万` → `amountCent=undefined`。**上限提到 20 万，光改数字没用。**
   另：`handleRecord` **没有**上限校验（只有 manual:538 / amend:645 有）；
   `arabic_bare` 另有 10 万粗筛（`asr-parse.js:116`）

### 产出：Wiki 新增一类页面
`docs/wiki/engineering/23-change-impact.md`（264 行）—— **变更影响面索引**，
按「你要改什么」组织：金额相关 / 分析相关 / 接口相关 / 前端相关 / 类目相关 / 部署校验。

- **`calcRecurringPatterns` 检不出月付订阅**（要求同末级类目≥3笔，月付单月只有1笔 → count:0）

### 总览页新增 §7「本 Wiki 的使用边界」
把上述结论固化进 `00-overview.md`，含推荐流程：
**Wiki（判断）→ grep（坐标）→ 改 → `npm test` + `npm run preflight`（守卫）**
纯找文件位置时**别读 Wiki**（grep 更快更准，Wiki 在这上是负收益）。

### 方法论教训（值得记住）
**「Wiki 有用」是个模糊断言，必须设计实验才能给出有价值的答案。**
第一反应是想当然认为「Wiki 覆盖得越多越有用」，实测证明：
**Wiki 的边际价值在于「判断题」，不在「坐标题」。**
坐标类信息（行号、常量名）写进 Wiki 反而会**过期**且**误导**（它会让人信一个错的坐标），
而判断类信息（铁律、纪律、非目标、坑）**才是 grep 拿不到的那部分**。
→ 结论：Wiki 应重点写「为什么这么设计」和「哪里会静默出错」，
     少写「在第几行」（行号引用只作为**佐证**，不能作为**导航**）。

## 定时任务触发链路核查（用户问「定时任务如何触发」）

**结论：链路是断的。定时触发器从未真正执行过 dailyInsight。**

### 断点（已实测验证，非推测）
官方定时触发器下发的 event 是
`{ Type:'Timer', TriggerName:'dailyInsight', Time:'...', Message:'' }`
—— **没有 `action` 字段**。
而 `cloudfunctions/analysis-svc/index.js:78` 是 `const { action, payload = {} } = event || {}`，
`action` 为 undefined → `switch` 落 `default` → 返回 `{ok:false, error:'未知操作: undefined'}`。

实测（临时 probe 脚本喂真实 event 结构，已删除）：
- 场景 A（官方真实 event）：`ok=false`，error=「未知操作: undefined」，落库 0 条
- 场景 B（测试用的 `{action:'dailyInsight'}`）：`ok=true`，processed=1，落库 1 条

**为什么测试全绿**：现有测试全部手工构造 `{action:'dailyInsight'}`，
绕过了「平台怎么下发 event」这一层 → 本地全绿 ≠ 云端能跑（又一条同型教训）。

### 修法（待实施）
在 `exports.main` 入口做**分发归一**：识别 `event.Type === 'Timer'`
（或 `event.TriggerName === 'dailyInsight'`）→ 映射成 `action='dailyInsight'`。
不要改 config.json 的 cron（cron 本身是对的：`0 0 0 * * * *` 7 段 = 每天 0 点 UTC+8）。

### 另外两个已确认的问题
1. **时区**：云函数运行时是 UTC+0，触发器 cron 是 UTC+8。
   `dailyInsight` 用 `dateUtil.toMonthStr(new Date())` 取月份 → 差 8 小时，
   **月初 0 点会算成上个月**。修法：环境变量 `TZ=Asia/Shanghai`（官方推荐），
   或代码内显式按东八区算。`shared/util/date.js` 全用本地时区，**不能只改云函数**。
2. **部署**：改 config.json 后要「云函数增量上传:更新文件」**再**「上传触发器」，
   两步是不同概念；只部署代码触发器不生效。
3. **preflight 的 Wiki 检查有洞**：`bad()` 只打印不 `hardFail++`
   → llms.txt 指向 7 个不存在的文件，退出码仍是 0（`tools/preflight.js:930`）。
   llms.txt 索引的 12 个页面只有 5 个真实存在。

## 落地「先查 Wiki」提问分流规则（三层 + 守卫）

**需求**：处理用户问题时，先渐进式查询 `docs/wiki/`。

**关键判断**：规则**不能**写成「一律先读 Wiki」。
`docs/wiki/00-overview.md` §7 的双盲对照实验已实测：
只读 Wiki 在判断题上 5/5 全对，在**坐标题**上大量推断错误；
只读源码在判断题上会跑偏 → **Wiki 提供「判断」，源码提供「坐标」**。
强制「一律先读」会让纯找位置的问题也翻 Wiki，而 Wiki 行号会随代码变动失效 —— **比 grep 更慢更不可靠**。
所以规则按**题型分流**：判断题先读 Wiki / 坐标题直接 grep / 口径题不问 Wiki（找产品）。

### 三层落地
| 层 | 文件 | 作用 |
|---|---|---|
| 静态 | `AGENTS.md` | 分流表 + 渐进下钻路径（llms.txt → 00-overview → 相关的 1~2 页 → grep → 源码） |
| **强制** | `.codebuddy/hooks/wiki-first.js` + `.codebuddy/settings.json` | `UserPromptSubmit` hook，每次提问注入规则 |
| 守卫 | `tools/preflight.js` 第 10b 段 | 规则资产缺失/注册丢失/JSON 坏 → `hardFail` |

### WorkBuddy hook 配置路径（实测得出，非文档推断）
文档写项目级 `.codebuddy/settings.json`，但**用户级实际是 `~/.workbuddy/settings.json`**。
从 app.asar 里挖到的证据链：
- `projectDirName` 默认常量 `S=".codebuddy"`，且 `dataLayout.configDir` **无人注入** → 默认值生效
- 受保护路径列表同时含 `~/.codebuddy/settings.json` 与 `~/.workbuddy/settings.json` → 两个都读
- `UserPromptSubmit` 在运行时真实存在，注入内容以 `<system-reminder data-role="hook">` 进上下文
- 记忆加载器常量 `L="AGENTS.md"` → **AGENTS.md 会被自动当项目级记忆读**

### hook 脚本的三条纪律
1. **stdout 只能输出协议 JSON**，调试一律走 stderr（混进去会破坏解析）
2. **按 `cwd` 判定**：项目根有 `docs/wiki/llms.txt` 才注入 → 换项目静默放行，可复用
3. **stdin 解析失败时不能回落 `process.cwd()`** —— 那会把「不属于本项目」的调用也注入了
   （实测踩到：stderr 说「跳过注入」但 stdout 仍注入了，自相矛盾）

### 验证方法（按项目纪律：不看它跑绿，要注入 bug）

## 修复定时任务（三处，版本 `20261031-02`）

### ① 入口分发归一（`analysis-svc/index.js` 的 `normalizeEvent()`）
官方触发器 event `{Type:'Timer', TriggerName, Time, Message}` **没有 `action`**，
而入口只认 `event.action` → 落 `default` → 返回「未知操作: undefined」。

`TriggerName` 对不上则拒绝（不误跑批量）；**`payload` 不透传**（防外部注入 month/cursor）。

### ② 月份时区（`shared/util/date.js` 新增 `toMonthStrCST()` / `toDateStrCST()`）
云函数运行时 UTC+0 vs cron UTC+8 → **每月 1 号会分析上个月**。
→ 固定 +8 小时偏移，**不依赖运行时 TZ，也不依赖控制台配没配 `TZ`**。
**没有改 `toMonthStr`** —— 它被 5 个云函数共用，改口径会波及一片。
且用 **`event.Time`（触发时刻）而非 `new Date()`** —— 权威、可复现、避免排队延迟跨月。

### ③ 部署是两步
「更新触发器文件」与「上传触发器」是**两个不同概念**。只部署代码触发器不生效。
（preflight 的云侧清单原来写「随部署生效」—— **那句话是错的**，已改。）

### ⚠️ 本次挖出的三个「测试本身有问题」（比目标 bug 更值得记）

**A. `test()` 不 await → 所有断言都没跑，却全绿通过**
同步 `try { fn(); } catch {}` 对 async 函数**不抛错** → 断言失败变成未捕获的 Promise 拒绝
→ catch 抓不到 → 「N 通过 / 0 失败」+ exit 0。
**修法三处缺一不可**：① `test()` 改 async + `await fn()`
② 加 `process.on('unhandledRejection')` ③ **用 `process.exitCode` 而非 `process.exit()`**
（`process.exit()` 立即终止进程，未处理的拒绝根本没机会触发 → 缺陷被吞）
且监听器里必须**直接设 `process.exitCode=1`**（只 `failed++` 没用，main 末尾已设过）。
→ 这就是「定时分析坏了很久没人发现」的真正原因。

**B. mock 不过滤条件 → 断言测的是 mock 不是代码**
`userCol.where()` 无视条件无条件返回全部；`command.gte/lte` 返回 `{}`。
→ 「跨月结果不算本月已分析」永远不成立。已让 mock 忠实还原云开发语义
（where 真过滤、gte().and(lte()) → {min,max}、delFlag 缺失视为未删除）。

**C. 本地时区 = Asia/Shanghai，恰好掩盖云端 UTC+0 的问题**
「退回本地时区」这种错误在本地**等价于正确的东八区** → 测不出来。
→ 加 `npm run test:tz-utc`（`process.env.TZ='UTC'` 跑一遍全部定时测试）。
断言要测**调用点**（dailyInsight 算出的月份），不只是测函数本身 ——
纯函数断言在注入「调用点改回本地时区」时照样通过。
